# AI RAG system with Edge Function tool calling and streaming chat

This phase adds a full RAG pipeline to the StockFlow AI assistant: a knowledge base backed by pgvector, ten domain-specific tools that query live Supabase data, an Edge Function that orchestrates OpenAI function-calling with provider fallback and SSE streaming, and a rewritten frontend with streaming markdown rendering, conversation history, and a floating widget. The approach is proxy-first — all AI provider calls route through the Deno Edge Function so API keys never touch the browser.

Watch for: The Edge Function calls `match_knowledge` with a `query_text` parameter that doesn't exist in the SQL function signature (confirmed). The in-memory rate limiter resets on every cold start, providing no real protection at scale (confirmed). The `useSearchKnowledge` hook passes a raw text string as `query_embedding` where the SQL function expects a `vector(1536)` (confirmed). User-supplied text is interpolated directly into PostgREST filter strings in the tool executor, which — while not classic SQL injection because PostgREST parameterizes — allows filter manipulation (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The `match_knowledge` RPC has a contract mismatch in two of three call sites. The SQL function requires a `vector(1536)` embedding as its first argument, but the Edge Function passes `{ query_text: query }` (a string) and the `useSearchKnowledge` hook passes `{ query_embedding: queryText }` (also a string). Only `knowledge-base.ts` calls it correctly by pre-generating the embedding. Both broken paths will fail at runtime, making the Edge Function's RAG context retrieval and the frontend search hook non-functional until fixed.

Rate limiting uses a module-scoped `Map` in a Deno isolate. Supabase Edge Functions cold-start frequently and may run multiple isolates, so this rate limit is per-isolate and resets on every cold start. A determined caller can trivially exceed 30 req/min. If rate limiting is a security requirement, it needs a durable store.

The Edge Function duplicates all 10 tool implementations that also exist in `tools-executor.ts`. The server-side copy runs under the service-role key (bypasses RLS), while the client-side copy runs under the user's session. Depending on which path is taken, the same question returns different data. There's no documentation of which is canonical or when the client-side path is used.

The `stopStream` function sets a ref flag but never calls `AbortController.abort()` on the underlying fetch. The HTTP connection stays open, the response body keeps streaming, and the Edge Function continues executing (and billing) until it finishes.

The IVFFlat index is created with `lists = 100` on a table with 8 seed rows. IVFFlat's recall degrades sharply when rows << lists; this index should be deferred or replaced with HNSW.

<details>
<summary>Issues (9)</summary>

1. **`match_knowledge` parameter mismatch in Edge Function** — The RPC call passes `query_text` which is not a parameter in the SQL function. Change to generate an embedding first or add a text-based overload to the SQL function.
2. **`useSearchKnowledge` passes raw text as vector** — The hook passes a string where `vector(1536)` is expected. Either generate an embedding client-side before calling the RPC, or expose a separate text-search endpoint.
3. **IVFFlat index with 8 rows** — Creating `lists = 100` on a table with 8 seed rows gives near-zero recall. Defer index creation or use HNSW.
4. **In-memory rate limiter is per-isolate** — Cold starts and multiple isolates mean the 30 req/min limit is not enforced globally. Move to a durable store.
5. **`stopStream` doesn't abort the HTTP connection** — Add an `AbortController` to the `streamChat` fetch and signal it from `stopStream`.
6. **Duplicated tool implementations (Edge Function vs client-side)** — The two copies implement the same 10 tools independently with different access levels. They will drift. Consider having the client always go through the Edge Function for tool execution.
7. **Filter string interpolation from AI-generated arguments** — Tool arguments from the LLM are interpolated into PostgREST `.or()` filter strings without sanitization. A value containing `,id.neq.` could manipulate the filter clause. Validate/escape tool arguments before interpolation.
8. **Missing embeddings Edge Function** — `embeddings.ts` references `/functions/v1/embeddings` but no such function exists in this diff. The entire client-side RAG path falls back to zero-vectors and never matches anything.
9. **Seed rows unmanageable via RLS** — The UPDATE policy requires `auth.uid() = created_by`, but seed rows have NULL `created_by`. No admin can update or deactivate seed entries via the API.

## `match_knowledge` contract mismatch

The SQL function is defined as:

```sql
CREATE OR REPLACE FUNCTION match_knowledge(
  query_embedding vector(1536),
  match_threshold FLOAT DEFAULT 0.7,
  match_count INT DEFAULT 5,
  filter_category TEXT DEFAULT NULL
)
```

The Edge Function calls it:

```typescript
const { data: rpcResults } = await supabaseClient.rpc('match_knowledge', {
  query_text: query,  // string, not vector(1536)
  match_count: 5,
});
```

There is no `query_text` parameter. PostgREST will reject the call or fail on the missing required `query_embedding`. The catch block silently swallows the error and falls through to tag-based search, meaning semantic search never fires from the Edge Function.

The `useSearchKnowledge` hook has the same bug — it passes the user's search string directly as `query_embedding`, so PostgREST will attempt to cast text to `vector(1536)` and fail.

## Stream abort gap

`useStreamMessage.stopStream()`:

```typescript
const stopStream = useCallback(() => {
  abortRef.current = true;
  setState((prev) => ({ ...prev, isStreaming: false }));
}, []);
```

`streamChat` in `streaming.ts`:

```typescript
const response = await fetch(AI_EDGE_FUNCTION_URL, {
  method: 'POST',
  headers,
  body: JSON.stringify({ ... }),
});
```

No `AbortController` is created or passed to `fetch`. The `abortRef` flag only suppresses React state updates but the ReadableStream reader loop continues until the server closes the connection. For tool-calling requests that trigger multiple LLM round-trips, this keeps the Edge Function executing for seconds after the user pressed stop.

## PostgREST filter interpolation from LLM output

In the Edge Function's `executeToolCall`:

```typescript
case 'check_stock': {
  const product = String(args['product_id'] || '');
  .or(`name.ilike.%${product}%,sku.ilike.%${product}%`)
```

`product` comes from `JSON.parse(toolCall.function.arguments)` — output of the LLM's function-calling response. The PostgREST filter DSL can be manipulated by a value containing commas and operators (e.g., `%,id.neq.`), injecting additional filter clauses. The same pattern exists in all 10 tool implementations.

For the service-role client (which the Edge Function uses), this means a hallucinated LLM response could broaden queries past what RLS would normally allow, since the service-role key bypasses RLS entirely.

## Dual tool executor divergence

The Edge Function holds a complete tool executor under the service-role key (bypasses RLS, sees all data). The client-side `src/services/ai/rag/tools-executor.ts` holds a duplicate that runs under the user's session (respects RLS). The `query-engine.ts` on the client side calls the local executor, but the streaming flow calls the Edge Function. There's no documentation of which path is authoritative.

## Missing embeddings Edge Function

`embeddings.ts` references `${SUPABASE_URL}/functions/v1/embeddings` but no `supabase/functions/embeddings/` directory exists in this diff. In development this falls back to zero vectors (all cosine distances are 0, nothing matches the threshold), making the client-side semantic search path inert.

## Knowledge base RLS vs seeded rows

The INSERT policy requires `auth.uid() = created_by`, but the seed data inserts rows with `created_by` as NULL. The UPDATE policy (`auth.uid() = created_by`) means no authenticated user can modify seed entries through the API. An admin-role policy or explicit `created_by` assignment is needed.
