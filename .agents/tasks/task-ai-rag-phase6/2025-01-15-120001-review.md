# AI RAG system with streaming chat, tool calling, and knowledge base (v2)

This is the second review pass after fixes to the Phase 6 AI/RAG implementation. The first pass surfaced 9 issues; 6 were addressed: the `match_knowledge` parameter mismatch in the Edge Function (now generates an embedding via OpenAI before calling the RPC), the `useSearchKnowledge` hook (switched to text-based ilike search), the IVFFlat index (deferred with documentation), the rate limiter (documented as per-isolate), the AbortController for stream cancellation (added), and the seed row RLS policy (added `OR created_by IS NULL`). The dual-implementation architecture in `tools-executor.ts` is now documented.

Watch for: The client-side `tools-executor.ts` still interpolates unsanitized strings into PostgREST `.or()` filters (confirmed) — the `sanitizeFilterValue` helper was added to the Edge Function but not to the client-side copy. The `knowledge-base.ts` passes embeddings as `JSON.stringify(array)` — a string — to the `match_knowledge` RPC that expects `vector(1536)` (likely; depends on whether PostgREST auto-casts stringified arrays to vectors). The client-side `context-builder.ts` interpolates user-derived keywords into `.or()` filters without sanitization (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The `sanitizeFilterValue` fix was applied only to the Edge Function's tool executor. The client-side `tools-executor.ts` and `context-builder.ts` still interpolate raw strings — derived from user queries via keyword extraction — directly into PostgREST filter expressions. Since the client-side path runs under the user's session (RLS-protected), the blast radius is smaller than the service-role path, but filter manipulation is still possible: a crafted query keyword like `%,id.neq.` would inject additional filter clauses and could expose records the query wasn't intended to return.

The `knowledge-base.ts` client-side search calls `match_knowledge` with `query_embedding: JSON.stringify(embeddingResult.embedding)` — a JSON string representation of the array. If PostgREST doesn't auto-cast it, the RPC will fail and the code falls through to text search, meaning semantic search is silently broken on the client path. The Edge Function's fix (which passes the raw array directly) is the correct approach.

The missing embeddings Edge Function (`/functions/v1/embeddings`) is documented but still doesn't exist. The client-side RAG path always returns zero-vectors from `generateEmbedding()`, so `searchKnowledge()` in `knowledge-base.ts` always falls through to text search. The Edge Function path works correctly because it calls OpenAI directly.

Both the Edge Function and the client write to `ai_conversations.messages` for the same conversation. Since both perform full-array overwrites (not appends), a race condition can cause duplicate or lost messages when the Edge Function's `saveConversation` and the client's `saveMessagesToConversation` complete near-simultaneously.

## Client-side filter interpolation without sanitization

The Edge Function now sanitizes tool arguments with `sanitizeFilterValue` before interpolation into `.or()` expressions. The client-side `tools-executor.ts` was not updated:

```typescript
// src/services/ai/rag/tools-executor.ts line 192
.or(`name.ilike.%${product}%,sku.ilike.%${product}%`)

// src/services/ai/rag/tools-executor.ts line 269
.or(`order_number.ilike.%${orderRef}%,id.eq.${orderRef}`)
```

The `context-builder.ts` has the same pattern:

```typescript
// src/services/ai/rag/context-builder.ts line 52
.or(`name.ilike.%${searchTerm}%,sku.ilike.%${searchTerm}%`)
```

These values come from `extractEntity()` in `query-engine.ts`, derived from user query keywords. A crafted input manipulates the filter logic to return unintended records from tables the user has SELECT access to. The fix: export `sanitizeFilterValue` from a shared utility and apply it in `tools-executor.ts`, `context-builder.ts`, and `knowledge-base.ts` (the fallback text search path).

## Embedding serialization mismatch in `knowledge-base.ts`

```typescript
// src/services/ai/rag/knowledge-base.ts line 45
const params: Record<string, unknown> = {
  query_embedding: JSON.stringify(embeddingResult.embedding),  // string "[0.1,0.2,...]"
  ...
};
const { data, error } = await supabase.rpc('match_knowledge', params);
```

The SQL function expects `query_embedding vector(1536)`. The Supabase JS client serializes RPC params to JSON for the HTTP body — if `query_embedding` is already a string, it gets double-quoted in the JSON payload (`"\"[0.1,0.2,...]\""` instead of `"[0.1,0.2,...]"`). The Edge Function's approach (passing the raw `number[]`) is correct:

```typescript
// supabase/functions/ai-chat/index.ts (fixed)
const embedding = await generateQueryEmbedding(query);  // returns number[]
await supabaseClient.rpc('match_knowledge', {
  query_embedding: embedding,  // raw array
});
```

Pass the raw array in `knowledge-base.ts` as well.

## Conversation save race condition

The Edge Function saves via `saveConversation()`:

```typescript
const updatedMessages = [
  ...existingMessages,
  { role: 'user', content: userMessage, timestamp: now },
  { role: 'assistant', content: assistantResponse, timestamp: now },
];
await supabaseClient.from('ai_conversations').update({
  messages: updatedMessages, ...
}).eq('id', conversationId);
```

The client saves after streaming completes:

```typescript
const finalMessages = [...updatedMessages, assistantMessage];
if (convId) {
  await saveMessagesToConversation(convId, finalMessages);
}
```

Both perform full-array overwrites. If the Edge Function completes first, the client's write (which doesn't include the Edge Function's appended messages from its perspective) may overwrite it — or vice versa, depending on timing. The simplest fix: remove the client-side save for streamed conversations and let the Edge Function be the sole writer, or have the client re-read the conversation after streaming completes.
