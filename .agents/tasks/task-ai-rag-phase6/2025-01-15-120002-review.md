## High-level view

Two non-blocking items remain after v1/v2 fixes. `addKnowledgeEntry` and `updateEntry` in `knowledge-base.ts` serialize embeddings with `JSON.stringify` before inserting into the `vector(1536)` column — this works because pgvector defines a text-to-vector cast, but it produces a double-serialized string in the PostgREST JSON body and diverges from the (now-correct) raw-array approach used in the RPC path.

Without the embeddings Edge Function deployed, any knowledge entries created via the client store zero-vector embeddings permanently. These entries will never appear in semantic search results even after the embeddings function is deployed, because there's no backfill mechanism for existing zero-vector rows.

## Embedding serialization in direct column writes

The `addKnowledgeEntry` function:

```typescript
embedding: JSON.stringify(embeddingResult.embedding),
```

And `updateEntry`:

```typescript
updatePayload['embedding'] = JSON.stringify(embeddingResult.embedding);
```

The Supabase JS client serializes the entire request body to JSON for the PostgREST call. When `embedding` is already a string (from `JSON.stringify`), the final JSON body contains `"embedding": "[0.1,0.2,...]"` — a quoted string. PostgREST passes this to PostgreSQL as text, and pgvector's `text → vector` cast handles parsing. If the raw array were passed instead (`"embedding": [0.1,0.2,...]`), PostgREST would send it as a JSON array which PostgreSQL also casts to vector. Maintaining two serialization strategies for the same type in the same file invites future confusion.

## Zero-vector storage without backfill

The `generateEmbedding` function in `embeddings.ts` returns zero-vectors when the embeddings Edge Function is unavailable — well-documented as intentional for development. The downstream implication: every knowledge entry created through the UI during development gets a zero-vector permanently stored. The `match_knowledge` function uses cosine distance with a 0.7 threshold; cosine distance from a zero-vector is mathematically undefined (division by zero in the magnitude), and pgvector returns NaN or maximum distance for zero-magnitude vectors.

When the embeddings Edge Function is eventually deployed, newly created entries will get real embeddings, but all previously created entries retain their zeros. A backfill script or a `BEFORE INSERT` trigger that generates embeddings server-side would prevent this gap from accumulating.
