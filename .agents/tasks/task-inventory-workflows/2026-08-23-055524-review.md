# Inventory workflow engine: transfers, receiving, adjustments, alerts

Phase 3 adds a complete inventory operations layer to StockFlow — warehouse-to-warehouse transfers with an approval chain, purchase order receiving with GRN generation, reason-tracked stock adjustments, and a low-stock alert system. The approach layers a service tier (Supabase queries with validation logic) over an existing trigger-based stock engine, adds TanStack Query hooks for each workflow, and delivers four new pages with the project's dark glassmorphism UI style. All pages currently operate on mock data embedded in the components themselves.

Watch for: Non-atomic multi-step transfer completions can leave inventory in a half-transferred state if any item fails mid-loop (confirmed). The adjustment reason filter uses string-matching against a `[reason]` tag embedded in the notes column — fragile and unsearchable by index (confirmed). No test framework exists; these workflows are verified only by TypeScript compilation.

**Verdict**: APPROVED

## High-level view

The transfer workflow follows a four-state machine (pending → approved → in_transit/completed, or rejected). Stock validation happens both at approval time and implicitly at completion time via `createMovement`, but the completion loop processes items sequentially without a transaction boundary, so a multi-item transfer can partially debit the source warehouse and fail midway, leaving items orphaned.

Receiving integrates with existing purchase orders, creating GRN records and per-item stock-in movements. The loop that creates GRN items + movements + PO item updates runs without a transaction wrapper, carrying the same partial-failure risk as transfers.

Adjustments prepend `[reason_code]` to the notes field of a stock movement, and filter queries use `ilike` against that prefix. This avoids a schema join but makes reason filtering impossible to index and brittle if notes ever contain bracket characters.

The four UI pages are self-contained with inline mock data and import mutation hooks for form submissions, ready for a live backend swap.

<summary>Issues (5)</summary>

1. **Non-atomic transfer completion** — `completeTransfer` iterates items creating paired movements without a transaction. If item N fails, items 1..N-1 have already debited the source. Wrap in a Supabase RPC or at minimum catch-and-rollback.
2. **Non-atomic PO receiving** — Same pattern in `receiveItems`: GRN items + movements + PO item updates run in a sequential loop. A mid-loop failure leaves partial state.
3. **Reason filter via notes prefix** — Adjustment reason is stored as a `[code]` prefix in the `notes` text column and filtered with `ilike`. This won't use an index, is fragile to user-entered brackets, and can't support compound queries (reason + free-text search). Consider adding a `reason` column to `stock_movements` or a join to `stock_adjustment_reasons`.
4. **No `in_transit` status path** — `completeTransfer` accepts `approved | in_transit` but nothing ever sets a transfer to `in_transit`. The state is defined in the CHECK constraint and TypeScript union but unreachable in the current code.
5. **RLS policies are role-only** — All new table policies check `auth.role() = 'authenticated'` with no ownership or branch scoping. Any authenticated user can view/modify any transfer or GRN across all branches.

## Transfer completion without transaction boundaries

`completeTransfer` iterates over transfer items in a `for...of` loop, calling `createMovement` twice per item (one 'transfer' debit from source, one 'in' credit to destination). Each `createMovement` is an independent Supabase insert. If the third item's debit fails due to insufficient stock, the first two items have already been debited from the source warehouse and credited to the destination. The transfer itself will not be marked completed (the final status update won't execute), but the inventory has already changed.

```typescript
for (const item of items) {
  await createMovement({ ... type: 'transfer', ... });  // debit source
  await createMovement({ ... type: 'in', ... });        // credit destination
  await supabase.from('stock_transfer_items').update(...)
}
// If loop breaks here, partial movements exist
const { data: updated } = await supabase.from('stock_transfers').update({ status: 'completed' })
```

The same pattern exists in `receiveItems` — each item gets a GRN record, a stock movement, and a PO item update in sequence. A failure partway through leaves the GRN partially populated and some PO items updated but not others.

A database-level RPC that handles the multi-item insert atomically would solve this. Alternatively, a compensation pattern (track created movements and delete them on failure) would work but adds complexity.

## Adjustment reason as notes prefix

`createAdjustment` stores the reason like this:

```typescript
notes: `[${input.reason}] ${input.notes ?? ''}`.trim()
```

Then `getAdjustmentHistory` filters with:

```typescript
query = query.ilike('notes', `%[${filters.reason}]%`);
```

This means: (1) Any user-entered notes containing `[damaged]` will false-positive match. (2) The `ilike` on a text column can't use a B-tree index; it will seq-scan at scale. (3) Compound filtering (reason + search text) requires parsing the prefix out. The stock_movements table currently has no `reason` column, but the trigger function doesn't reference one either, so adding a nullable column would be safe.

## Unreachable `in_transit` status

The CHECK constraint and TypeScript union both define `in_transit` as a valid transfer status. `completeTransfer` accepts transfers in `approved` or `in_transit` state. But no code path ever sets a transfer to `in_transit` — `approveTransfer` moves directly to `approved`, and `completeTransfer` moves to `completed`. The status exists as a placeholder for a future "shipment tracking" step but is unreachable today.

## RLS grants full access to all authenticated users

Every new table's RLS policy uses `auth.role() = 'authenticated'` for both SELECT and INSERT/UPDATE. Any logged-in user can view all transfers across all warehouses, approve their own transfers, or create GRNs for any PO. The existing profile/role system has branch-level scoping and a permissions object on the `roles` table, but none of that is enforced at the database level for the new tables — a security gap for production deployment.

## Dashboard KPI card displacement

The dashboard replaced "Active Deals" and "Pending Orders" KPIs with "Pending Transfers" and "POs to Receive" — both using hardcoded values. This changes the dashboard's focus from a combined CRM+inventory view to inventory-dominant, removing CRM visibility from the top-level summary.
