# PHP backend, data hooks, and AI Edge Function for StockFlow (v3)

Third and final review pass. All five v2 issues are resolved: the shipping webhook returns 503 when secret is unconfigured (fail-closed), the email attachments parameter is removed from the public API, the cron scheduler uses `exec()` for subprocess isolation, the daily stock report attaches the generated PDF to the email, and the invoice fallback format matches the primary 4-digit pattern.

Watch for: The Razorpay webhook has the same empty-secret vulnerability that the shipping webhook previously had — `hash_hmac('sha256', $payload, '')` produces a deterministic hash that an attacker can forge when `RAZORPAY_WEBHOOK_SECRET` is unset (confirmed). The `ExcelController` import inserts rows one-by-one via individual HTTP requests to PostgREST, which will be extremely slow for large files — the exact scenario this endpoint exists to handle (confirmed). The `AuthMiddleware` will throw an opaque `firebase/php-jwt` error if `SUPABASE_JWT_SECRET` is empty, rather than failing with a clear startup message (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The Razorpay webhook route verifies HMAC-SHA256 signatures, but the `PaymentService` uses the webhook secret directly from config which defaults to empty string. Unlike the shipping webhook (which now explicitly rejects when unconfigured), the Razorpay path will happily verify against the empty-string key. An attacker who sends `X-Razorpay-Signature: hash_hmac('sha256', body, '')` bypasses verification on any deployment that hasn't configured the secret.

The Excel import endpoint's design contradicts its purpose. The routing layer in `src/services/excel/routing.ts` sends files >5MB to the PHP backend for "server-side processing", but the controller iterates over parsed rows and issues one `SupabaseService::insert()` HTTP call per row. A 10,000-row spreadsheet makes 10,000 individual REST API calls to Supabase. PostgREST supports bulk insert via array POST bodies, which would reduce this to ~100 calls at the existing batch size.

## Razorpay webhook empty-secret bypass

`PaymentService::verifyWebhookSignature()`:

```php
public function verifyWebhookSignature(string $payload, string $signature): bool
{
    $expectedSignature = hash_hmac('sha256', $payload, $this->webhookSecret);
    return hash_equals($expectedSignature, $signature);
}
```

When `$this->webhookSecret` is `''` (the default from `$_ENV['RAZORPAY_WEBHOOK_SECRET'] ?? ''`), the HMAC is computed against an empty key. PHP's `hash_hmac` does not reject empty keys — it produces a valid hash. An attacker who knows the secret is empty can compute the correct signature for any payload. The shipping webhook was fixed to return 503 in this case; the Razorpay path needs the same treatment. Either guard in `WebhookController::razorpay()` before calling `verifyWebhookSignature`, or have `PaymentService` reject the empty-secret case internally.

## Excel import N+1 HTTP pattern

`ExcelController::import()` already chunks rows into groups of 100, but then iterates within each chunk:

```php
foreach (array_chunk($data, $batchSize) as $batch) {
    foreach ($batch as $index => $row) {
        try {
            $this->supabase->insert($targetTable, $row);
            $inserted++;
        } catch (\Throwable $e) { ... }
    }
}
```

Each `$this->supabase->insert()` is a separate Guzzle POST to `{supabase_url}/rest/v1/{table}`. PostgREST accepts array JSON bodies for bulk insert — a single POST with 100 records in the body is ~100x faster than 100 individual requests. The `SupabaseService` class only has a single-record `insert()` method. Adding a `bulkInsert(string $table, array $rows)` that POSTs the full array would align the implementation with the routing layer's intent (handle large files server-side for performance).
