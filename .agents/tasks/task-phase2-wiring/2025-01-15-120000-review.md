# PHP backend, data hooks, and AI Edge Function for StockFlow

This change adds a full PHP Slim 4 backend service (`server/php/`) with PDF generation, email, Excel processing, payment webhooks, and WhatsApp notifications. Fourteen TanStack Query hooks wire the React frontend to Supabase for all domain entities. A Supabase Edge Function proxies AI requests to OpenAI/Gemini/Anthropic with JWT auth. Docker composition grows from one service to three (frontend, php-backend, cron).

Watch for: The cron service references `cron/scheduler.php` which does not exist (confirmed). Docker SMTP env vars (`SMTP_USER`/`SMTP_PASS`) don't match the names `settings.php` reads (`SMTP_USERNAME`/`SMTP_PASSWORD`) — email will silently fail in Docker (confirmed). The shipping webhook endpoint has no signature verification or authentication (confirmed). CORS middleware sends `Access-Control-Allow-Credentials: true` with `Access-Control-Allow-Origin: *` when origin isn't in the allowlist, which browsers reject (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The PHP backend is a Slim 4 app with DI container and route groups. Auth middleware validates Supabase JWTs via firebase/php-jwt. Webhook routes sit outside the auth group so payment/shipping callbacks can reach the app, but the shipping endpoint performs no verification of its own — it blindly trusts any POST body. The Razorpay webhook correctly verifies HMAC-SHA256 signatures.

The fourteen frontend hooks follow a consistent pattern: paginated queries with filters, single-item fetch, CRUD mutations that invalidate related query keys. The notification hook subscribes to Supabase Realtime per-user. None of the hooks guard against missing auth sessions, which will throw on first page load before login — though TanStack Query's error retry likely papers over this in practice.

The AI edge function validates the JWT by calling `getUser()` on the Supabase admin client, routes to the configured provider, and persists conversations. A read-then-write pattern on the conversation messages array creates a theoretical race window under concurrent requests.

Docker env var naming diverges between the compose file and the PHP settings loader for SMTP and Twilio credentials, and the cron service's entrypoint invokes a file that was never created, so `docker compose up` will crash on the cron container.

<summary>Issues (7)</summary>

1. **Missing `cron/scheduler.php`** — docker-compose cron service entrypoint references `cron/scheduler.php` which doesn't exist. Create the file or change the entrypoint to run individual cron scripts.
2. **SMTP env var mismatch** — Docker passes `SMTP_USER`/`SMTP_PASS`; `settings.php` reads `SMTP_USERNAME`/`SMTP_PASSWORD`. Align the names. Same issue for `TWILIO_SID` vs `TWILIO_ACCOUNT_SID`.
3. **Unauthenticated shipping webhook** — `POST /api/webhooks/shipping` performs no signature verification or token check. Add shared-secret HMAC verification or IP allowlist.
4. **CORS credentials + wildcard** — `CorsMiddleware` returns `Allow-Credentials: true` alongside `Allow-Origin: *` for unrecognized origins. Browsers block this combination. Either omit credentials header when origin isn't matched, or reject the request.
5. **Invoice number collision risk** — `generateInvoiceNumber()` uses `random_int(1, 9999)`. Under concurrent load, duplicates are likely. Use a DB sequence or atomic counter.
6. **Frontend VITE_ vars not available at Docker runtime** — The frontend Dockerfile bakes env vars at build time. The `docker-compose.yml` `environment:` block for the frontend service won't propagate `VITE_*` vars into the already-built static bundle.
7. **Rate limiter resets on deploy** — In-memory static array (`$requestCounts`) doesn't survive PHP-FPM worker boundaries or restarts. Acceptable for development but ineffective in production.

## Shipping webhook trust boundary

The Razorpay webhook endpoint verifies the `X-Razorpay-Signature` header before processing:

```php
if (!$this->paymentService->verifyWebhookSignature($rawBody, $signature)) {
    return Response::error($response, 'Invalid webhook signature', 401);
}
```

The shipping webhook at the same path prefix has no equivalent. It accepts any POST with `tracking_number` and `status` fields and directly writes to `sales_orders` and `notifications`. An attacker who discovers the endpoint can inject arbitrary shipping status changes and create spurious notifications. Since this route is outside the auth group (alongside Razorpay, which self-verifies), no middleware protects it either.

## Docker environment naming divergence

`settings.php` reads:
```php
'username' => $_ENV['SMTP_USERNAME'] ?? '',
'password' => $_ENV['SMTP_PASSWORD'] ?? '',
```

`docker-compose.yml` passes:
```yaml
- SMTP_USER=${SMTP_USER}
- SMTP_PASS=${SMTP_PASS}
```

The `.env.example` at root uses `SMTP_USER`/`SMTP_PASS`. The PHP `.env.example` uses `SMTP_USERNAME`/`SMTP_PASSWORD`. When running via Docker, the PHP app will see `SMTP_USER` in `$_ENV` but look for `SMTP_USERNAME`, falling through to the empty-string default. Emails will fail with authentication errors.

The same pattern affects Twilio: compose passes `TWILIO_SID` but settings.php reads `TWILIO_ACCOUNT_SID`.

## Missing cron scheduler

The docker-compose cron service runs:
```yaml
entrypoint: ['sh', '-c', 'while true; do php /var/www/html/cron/scheduler.php; sleep 60; done']
```

The actual files in `server/php/cron/` are `daily-stock-report.php`, `overdue-payments.php`, `lead-followup-reminder.php`, and `backup-trigger.php`. No `scheduler.php` exists. The cron container will exit with a PHP fatal error on startup.

## CORS Allow-Credentials with wildcard origin

When the incoming `Origin` header doesn't match any entry in `$allowedOrigins`, `CorsMiddleware::addCorsHeaders` falls through to:
```php
$allowedOrigin = '*';
```

Then unconditionally appends:
```php
->withHeader('Access-Control-Allow-Credentials', 'true')
```

Per the Fetch spec, `Access-Control-Allow-Credentials: true` is incompatible with `Access-Control-Allow-Origin: *`. Browsers will reject the preflight response. The credential header should only be set when a specific origin is reflected.

## Invoice number generation

```php
private function generateInvoiceNumber(): string
{
    $year = date('Y');
    $sequence = str_pad((string) random_int(1, 9999), 4, '0', STR_PAD_LEFT);
    return "INV-{$year}-{$sequence}";
}
```

With 9,999 possible values per year and no uniqueness check, the probability of collision grows quickly under normal usage. If the `invoices` table has a unique constraint on `invoice_number`, the insert will fail and the user gets a 500. If it doesn't, duplicate invoices are silently created. A database-backed sequence (or Supabase RPC that atomically increments a counter) would be safer.

## Frontend Vite build-time vars in Docker

The frontend Dockerfile runs `pnpm build` during the image build stage. Vite inlines `VITE_*` env vars at build time via `import.meta.env`. The `environment:` block in docker-compose only affects the running container's OS environment, which nginx doesn't expose to the static JS bundle. The Supabase URL and PHP API URL will be whatever was present (or absent) when the image was built, not what's in `.env` at compose-up time.

The default `docker compose up` workflow documented in the README won't work without passing build args or rebuilding with the correct env vars baked in.

## Edge Function conversation storage race condition

When updating an existing conversation, the function fetches current messages then appends:
```typescript
const { data: existing } = await supabaseClient
  .from('ai_conversations')
  .select('messages')
  .eq('id', conversationId)
  .single();

const updatedMessages = [...existingMessages, newUserMsg, newAssistantMsg];
await supabaseClient.from('ai_conversations').update({ messages: updatedMessages })...
```

If two requests arrive concurrently for the same conversation (possible with rapid clicks or retries), one update overwrites the other's appended messages. A JSONB array-append RPC would eliminate the race. Practical risk is low for single-user conversations but worth noting for correctness.
