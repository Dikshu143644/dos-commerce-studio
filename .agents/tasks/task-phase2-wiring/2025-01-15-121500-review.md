# PHP backend, data hooks, and AI Edge Function for StockFlow (v2)

This is the second review pass after all seven v1 issues were addressed. The cron scheduler now exists with time-based dispatch and file locking. Env var names are aligned across docker-compose, .env.example, and settings.php. The shipping webhook verifies HMAC-SHA256 signatures. CORS no longer sends credentials with wildcard origin. Invoice numbers use a date-based sequence with DB uniqueness checks and retry. VITE_ vars are wired through Docker build args. The rate limiter documents its in-memory limitation.

Watch for: Shipping webhook verification is bypassed when `SHIPPING_WEBHOOK_SECRET` is empty (confirmed) — an unconfigured deployment accepts unauthenticated shipping callbacks. The `EmailController` accepts an `attachments` array from the request body and passes file paths directly to PHPMailer (confirmed) — an authenticated user can attach and exfiltrate arbitrary server files.

**Verdict**: NEEDS_CHANGES

## High-level view

The shipping webhook's HMAC verification gates on `!empty($this->shippingWebhookSecret)`. If the secret is unset (default empty string in settings.php), the entire signature check is skipped and the endpoint reverts to its pre-fix unauthenticated state. Deployments that don't configure this secret get no protection, with no warning.

The email endpoint validates template names against an allowlist but passes the `attachments` array from the HTTP request body directly to PHPMailer's `addAttachment()`. Any authenticated user can specify arbitrary server paths (e.g., `/var/www/html/src/Config/settings.php`) and receive their contents as email attachments — escalating from authenticated user to full service credential access.

The cron scheduler uses `require` to execute task scripts in-process, so state leaks between tasks in the same loop iteration. The daily stock report generates a PDF but never attaches it to the email it sends.

The invoice number fallback format (`INV-{year}-{8-digit-hrtime}`) doesn't match the primary format's length (`INV-{year}-{4-digit}`), which may confuse downstream consumers or violate column width constraints.

## Shipping webhook bypass on empty secret

The v1 fix added HMAC-SHA256 verification, but it's wrapped in a conditional:

```php
if (!empty($this->shippingWebhookSecret)) {
    $signature = $request->getHeaderLine('X-Shipping-Signature');
    // ... verify ...
}
```

The `settings.php` default is `$_ENV['SHIPPING_WEBHOOK_SECRET'] ?? ''`, so any deployment that hasn't configured this variable (including first-time Docker setups following the `.env.example` which has it blank) will silently skip verification. The Razorpay webhook doesn't have this problem because its verify method always performs a hash comparison regardless of secret value. The shipping path should either fail closed (reject requests when no secret is configured) or emit a visible warning at startup.

## Arbitrary file exfiltration via email attachments

`EmailController::send()`:

```php
$attachments = (array) ($body['attachments'] ?? []);
$this->emailService->send($to, $subject, $template, $data, $cc, $attachments);
```

Inside `EmailService::send()`:

```php
foreach ($attachments as $attachment) {
    if (file_exists($attachment)) {
        $mail->addAttachment($attachment);
    }
}
```

The `$to` address is also user-controlled. An authenticated user can POST `{"to": "attacker@example.com", "subject": "x", "template": "welcome.html", "attachments": ["/var/www/html/src/Config/settings.php"]}` and receive the settings file (containing all API keys and secrets) as an email attachment. The fix is either removing the `attachments` field from the API entirely (the frontend `phpApi` client doesn't expose it), or restricting paths to the `storage/` directory with a `realpath()` + prefix check.

## Cron task isolation via `require`

```php
foreach ($tasksToRun as $task) {
    try {
        require $file;
    } catch (\Throwable $e) { ... }
}
```

Each cron script loads its own `$settings` variable into the same scope. The `require` approach means a fatal error or seg-fault in one task kills the entire scheduler loop, and non-fatal side effects (shutdown handlers, altered error reporting, changed working directory) leak into subsequent tasks. Running each task as a subprocess (`php $file`) would provide process-level isolation.

## Daily stock report generates unused PDF

`daily-stock-report.php` calls `$pdfService->generate(...)` to produce a PDF file, then sends a separate plain-text HTML email via `$emailService->sendRaw()`. The PDF sits on disk but is never attached to the email or referenced anywhere else. Either pass the `$pdfPath` as an attachment to the email, or remove the PDF generation to avoid unnecessary disk writes.
