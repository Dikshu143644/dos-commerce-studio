# Sales workflow v3: stock deduction, invoicing, returns, and payments

All nine issues from v1 and v2 have been addressed. The `rollbackReservations()` helper in `confirmOrder` tracks and reverses prior reservations on mid-loop conflict. The invoice UPDATE RLS policy is now guarded by a `BEFORE UPDATE` trigger (`restrict_invoice_update_columns`) that resets protected columns for non-manager users. The `shipOrder` and `cancelOrder` reservation-release paths now check `.select('id')` result length and throw on mismatch, preventing silent leaks.

Watch for: The `shipOrder` function commits stock movements before releasing reservations — if a reservation release throws mid-loop (concurrent modification), movements are already persisted but the order stays in its pre-ship status, leaving inventory deducted with no shipped order to account for it (confirmed). The invoice column-protection trigger doesn't guard the legacy `amount` column, so a non-manager client could overwrite `invoices.amount` directly (confirmed, low severity — service layer never writes this field, and `total_amount` is the authoritative column).

**Verdict**: APPROVED

## High-level view

The service layer's state machine (draft → confirmed → processing → shipped → delivered) is well-structured with proper status guards at each transition. The `rollbackReservations` compensating action in `confirmOrder` addresses the primary atomicity concern from v2 — it reverses already-committed reservations on conflict, preventing orphans even though there's no true transaction boundary.

The column-level trigger on invoices is a pragmatic solution: PostgreSQL RLS can't restrict by column, so the `SECURITY DEFINER` trigger intercepts the row before write and resets protected fields to their `OLD` values for non-manager users. The one oversight is the `amount` column (distinct from `total_amount`), which isn't in the protected list. Since the service layer uses `total_amount` as the authoritative value and never writes `amount` post-creation, this is cosmetic rather than exploitable.

The remaining architectural gap is that `shipOrder` performs stock deductions (batch insert into `stock_movements`) and reservation releases (per-item optimistic update) as separate non-transactional steps. If a release fails after movements are committed, the function throws but leaves the movements in place. A subsequent retry would re-insert the same movements. This pattern is acceptable for an MVP with a single-user-at-a-time workflow but becomes a data integrity risk under concurrent operations on the same order.

## Shipment atomicity: movements committed before reservation release

In `fulfillment.ts`, `shipOrder` executes these steps in sequence:

```typescript
// Step 1: Batch insert stock movements (all-or-nothing for this single call)
const { error: movementError } = await supabase
  .from('stock_movements')
  .insert(movements);

// Step 2: Release reservations per-item (sequential loop with optimistic guard)
for (const item of items) {
  // ... read reserved_quantity, compute newReserved ...
  const { data: releaseResult } = await supabase
    .from('inventory')
    .update({ reserved_quantity: newReserved })
    .eq('reserved_quantity', expectedReserved)
    .select('id');

  if (!releaseResult || releaseResult.length === 0) {
    throw new Error(`Failed to release reserved stock...`);
  }
}

// Step 3: Update order status to 'shipped'
```

If Step 2 throws on item 3 (concurrent modification), the `stock_movements` from Step 1 are committed. The `update_stock_quantity` trigger has already decremented `inventory.quantity` for all items. But the order is still in `processing`/`confirmed` status because Step 3 never runs. The items still show as reserved (some released, some not), and the physical stock is already deducted.

Retrying `shipOrder` would:
- Re-insert the same movements (double deduction)
- Attempt to release reservations that may already be partially released

This is a recoverable situation with manual intervention (admin deletes duplicate movements), but it's not self-healing. The recommended fix: release reservations first (they can be re-reserved if the movement insert fails), then batch-insert movements, then update status. Alternatively, wrap both operations in a `plpgsql` function.

## Invoice trigger column coverage

The `restrict_invoice_update_columns` trigger resets these columns for non-managers:

```sql
NEW.invoice_number := OLD.invoice_number;
NEW.sales_order_id := OLD.sales_order_id;
NEW.customer_id := OLD.customer_id;
NEW.total_amount := OLD.total_amount;
NEW.tax_amount := OLD.tax_amount;
NEW.subtotal := OLD.subtotal;
NEW.discount_amount := OLD.discount_amount;
NEW.due_date := OLD.due_date;
NEW.notes := OLD.notes;
NEW.pdf_url := OLD.pdf_url;
NEW.generated_at := OLD.generated_at;
NEW.created_at := OLD.created_at;
```

Columns deliberately left mutable: `amount_paid`, `payment_status`, `paid_at`, `status`, `updated_at`. These are exactly what the payment flow needs.

The `amount` column (inherited from the original `invoices` table schema — the pre-Phase-5 total) is not in either list. Adding `NEW.amount := OLD.amount;` would close this gap.
