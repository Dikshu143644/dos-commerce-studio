# Sales workflow: stock deduction, invoicing, returns, and payments

This change implements the complete Phase 5 sales workflow on top of the existing Supabase-backed SPA. It adds a service layer that orchestrates order confirmation (with stock reservation), fulfillment (stock deduction via `stock_movements`), invoice auto-generation via the PHP backend, partial/full payment recording, and goods returns with stock restoration. A database migration extends the `invoices` table and creates `payments`, `sales_returns`, and `sales_return_items` tables. The UI receives full rewrites of SalesOrders and Invoices pages (removing all mock data) plus new Returns and Payments pages.

Watch for: Stock reservation in `confirmOrder` is non-atomic — a read-then-write loop with no server-side locking, creating a race window where two concurrent confirms can over-reserve the same stock (confirmed). All user-identifying fields (`confirmed_by`, `shipped_by`, `received_by`) are hardcoded to the string literal `'current_user'` instead of the authenticated user's UUID, which will produce FK violations or meaningless audit logs once real auth is wired (confirmed). The `confirmOrder` function calls an RPC `increment_reserved_quantity` that does not exist in any migration, silently falling back to the same read-then-write pattern (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The service layer is structured as five modules (orders, fulfillment, invoices, returns, payments) that compose a state machine over sales orders: draft → confirmed → processing → shipped → delivered, with cancel and return exits. Stock deduction relies on the existing `stock_movements` trigger (`update_stock_quantity`) to auto-decrement inventory quantities, so the service only needs to insert movement records. Invoice creation delegates PDF generation to the PHP backend and tolerates failure gracefully, storing a DB record regardless.

The critical gap is atomicity. Each service function performs multi-row mutations in a JavaScript for-loop issuing independent Supabase calls. There's no transaction boundary — if the third item in a five-item order fails during shipment, the first two movements are already committed, leaving inventory in an inconsistent state with no rollback path.

The RLS posture is intentionally broad: all new tables grant full access to any authenticated user, consistent with the project's existing pattern. However, the `payments` table only has SELECT and INSERT policies — the service layer calls `.update()` on `invoices` after recording a payment, which requires the existing `invoices_manage` policy (managers+ only). Staff-level users who can insert payments cannot update invoice amounts, creating a silent fail-closed behavior where the payment is recorded but the invoice balance is never updated.

The UI passes `'current_user'` as a literal string wherever a user UUID is required. This compiles fine (typed as `string`) but will violate FK constraints on `profiles(id)` at runtime or produce garbage audit trails. The real user ID from `useAuth()` or the Supabase session needs to flow through.

1. **Non-atomic stock reservation** — `confirmOrder` reads `reserved_quantity`, adds, then writes it back per item with no row-level lock or transaction. Two concurrent confirmations can over-reserve the same stock. Wrap in an RPC or use a single `UPDATE ... SET reserved_quantity = reserved_quantity + $1 WHERE quantity - reserved_quantity >= $1` with a check on affected rows. (confirmed)
2. **Non-atomic shipment movements** — `shipOrder` inserts stock movements in a loop. A mid-loop failure leaves partial deductions committed with no rollback. Use a Supabase database function or batch insert within a transaction. (confirmed)
3. **Phantom RPC `increment_reserved_quantity`** — Called in `confirmOrder` but never defined in any migration. The fallback is the same non-atomic read-then-write, so the RPC path is dead code. Either add the function to the migration or remove the RPC call entirely. (confirmed)
4. **Hardcoded `'current_user'` strings** — Every mutation in SalesOrders.tsx passes `'current_user'` instead of the authenticated user's UUID. This will fail FK constraints or produce meaningless audit logs. Wire `useAuth().user.id` through. (confirmed)
5. **Payment INSERT succeeds but invoice UPDATE may fail silently** — `payments` has INSERT policy for all authenticated users, but `invoices_manage` requires manager+ role. A staff user recording a payment will insert the payment row but the subsequent `invoices.update()` call will be silently rejected by RLS, leaving `amount_paid` stale. (likely)
6. **Return stock restoration targets arbitrary warehouse** — `approveReturn` takes `warehouse_id` from the input, not from the original sales order's warehouse. Returned stock could be credited to a different warehouse than it was deducted from, causing inventory mismatch. (confirmed)

## Non-atomic stock operations in confirmOrder and shipOrder

The `confirmOrder` function checks stock availability and reserves it in a per-item loop:

```typescript
for (const item of items) {
  const { data: current } = await supabase
    .from('inventory')
    .select('reserved_quantity')
    .eq('product_id', item.product_id)
    .eq('warehouse_id', warehouseId)
    .single();

  if (current) {
    await supabase
      .from('inventory')
      .update({ reserved_quantity: current.reserved_quantity + item.quantity })
      ...
  }
}
```

Between the SELECT and the UPDATE, another request can read the same `reserved_quantity` value and write its own increment. The function first tries `supabase.rpc('increment_reserved_quantity')`, but this RPC does not exist in any migration, so it always errors and falls through to the manual path. The fallback is identical in behavior, so there's no protection either way.

The same pattern appears in `shipOrder` for stock movement inserts and reservation release, and in `cancelOrder` for reservation release. In `shipOrder`, a failure partway through the loop leaves stock movements committed for earlier items with no compensating action.

The fix is either a Supabase database function that performs the entire multi-row operation in a single transaction, or at minimum using `UPDATE inventory SET reserved_quantity = reserved_quantity + $1 WHERE product_id = $2 AND warehouse_id = $3 AND quantity - reserved_quantity >= $1` and checking that the affected row count equals the expected count.

## Hardcoded user identity

Every action in `SalesOrders.tsx` passes a literal string where a UUID is expected:

```typescript
confirmOrder.mutate({ order_id: selectedOrderId, confirmed_by: 'current_user' });
shipOrder.mutate({ order_id: selectedOrderId, shipped_by: 'current_user' });
cancelOrder.mutate({ order_id: selectedOrderId, cancelled_by: 'current_user' });
recordPayment.mutate({ ..., received_by: 'current_user' });
```

The `audit_logs.user_id` column is `UUID` type with a FK to `profiles(id)`. Inserting `'current_user'` will fail with a UUID parse error at the database level. Even if audit log insertion is fire-and-forget (the service catches no error from it), the audit records won't be created. The `payments.received_by` column also has a FK to `profiles(id)` — this will cause the payment insertion itself to fail.

## Invoice-payment RLS asymmetry

The `recordPayment` service function inserts the payment (succeeds for any authenticated user) then calls `supabase.from('invoices').update(...)` to set `amount_paid` and `payment_status`. The `invoices_manage` policy from 002_rls_policies.sql restricts all operations to `super_admin`, `admin`, `manager`:

```sql
CREATE POLICY invoices_manage ON invoices FOR ALL USING (
    get_user_role() IN ('super_admin', 'admin', 'manager')
);
```

For a staff-level user, this update is silently rejected by RLS — Supabase returns `{ data: null, count: 0 }` rather than an error. The code checks `if (updateError)` but an RLS filter isn't an error; it's a silent no-op. The payment amount is recorded but the invoice balance never reflects it, producing a divergence between `sum(payments.amount)` and `invoices.amount_paid`.

## Return stock restoration warehouse mismatch

`approveReturn` accepts `warehouse_id` as an input parameter and uses it for all return stock movements:

```typescript
export async function approveReturn(input: ApproveReturnInput): Promise<SalesReturn> {
  for (const item of returnItems) {
    await supabase.from('stock_movements').insert({
      product_id: item.product_id,
      warehouse_id: input.warehouse_id,  // <-- caller-specified
      type: 'return',
      ...
    });
  }
}
```

The function doesn't look up the original sales order to determine which warehouse the goods were shipped from. If the caller specifies a different warehouse, stock is credited to the wrong location — a net loss in the original warehouse and phantom stock in the target.

## Migration: dual status columns on invoices

The migration adds `payment_status` alongside the existing `status` column on `invoices`. Both accept overlapping values (`'paid'`, `'partial'`, `'refunded'`). The `recordPayment` service updates both columns in lockstep (`updateData.status = 'paid'` alongside `updateData.payment_status = 'paid'`). If the intent is to track document lifecycle separately from payment lifecycle, there should be cases where they diverge — but the current code never separates them. This isn't blocking, but it's worth clarifying which column is authoritative for payment state and whether both need to exist.

## Test coverage

No automated tests exist for this change. Verification was `tsc -b` and `vite build` only. The race conditions, RLS asymmetry, and warehouse mismatch would be caught by integration tests.

Not tested: concurrent stock reservation, payment recording by non-manager roles, return to wrong warehouse, mid-shipment failure recovery, invoice generation when PHP backend is unavailable.
