# Sales workflow v2: stock deduction, invoicing, returns, and payments

All six issues from the v1 review have been addressed. Stock reservation now uses optimistic concurrency control (conditional update on `reserved_quantity`). Shipment and return stock movements use batch `.insert()`. The phantom `increment_reserved_quantity` RPC call is gone. All UI pages wire `useAuth().user.id` through to mutations. An RLS UPDATE policy was added for invoices. `approveReturn` looks up the original order's warehouse before using the caller-provided fallback.

Watch for: The `confirmOrder` reservation loop still has a partial-commit exposure — if item N fails the optimistic concurrency check, items 1..(N-1) are already reserved with no compensating rollback (confirmed). The new `"Auth update invoices for payments"` RLS policy grants unrestricted UPDATE on all invoice columns to any authenticated user, not just `amount_paid` and `payment_status` (confirmed). Reservation release in `shipOrder` and `cancelOrder` silently drops the update when the optimistic guard doesn't match, leaving phantom reservations (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The optimistic concurrency control in `confirmOrder` correctly detects conflicts on a per-item basis — if `reserved_quantity` changed between the read and the update, the update matches zero rows and the function throws. But the loop processes items sequentially, so items already reserved before a conflict remain reserved. The order stays in `draft` status (the status update comes after the loop), so the reserved quantities are orphaned — no future cancel or ship operation will release them because those flows check `order.status`.

The new invoice UPDATE RLS policy (`"Auth update invoices for payments"`) solves the v1 issue where non-managers couldn't update invoice balances, but it's column-unrestricted. Any authenticated user can now update `status`, `total_amount`, `due_date`, `notes`, or any other column on any invoice. The service layer only writes `amount_paid` and `payment_status`, but the policy doesn't enforce that boundary — a rogue client or compromised session can overwrite arbitrary invoice fields.

Reservation release during shipment and cancellation uses the same optimistic guard pattern (`eq('reserved_quantity', expectedReserved)`) but unlike `confirmOrder`, it doesn't check whether the update matched any rows. If the guard fails (concurrent modification), the reserved quantity is never decremented — a slow inventory leak that accumulates silently over time, reducing available stock.

## Partial reservation orphan on conflict in confirmOrder

The reservation loop in `orders.ts` (lines 155–189) processes items sequentially:

```typescript
for (const item of items) {
  const { data: inv } = await supabase
    .from('inventory')
    .select('reserved_quantity')
    .eq('product_id', item.product_id)
    .eq('warehouse_id', warehouseId)
    .single();

  const expectedReserved = inv.reserved_quantity;
  const newReserved = expectedReserved + item.quantity;

  const { data: reserveResult } = await supabase
    .from('inventory')
    .update({ reserved_quantity: newReserved })
    .eq('reserved_quantity', expectedReserved)  // optimistic guard
    .select('id');

  if (!reserveResult || reserveResult.length === 0) {
    throw new Error(`Stock reservation conflict...`);
  }
}
```

When the conflict throw fires on item 3, items 1 and 2 already have incremented `reserved_quantity`. The function doesn't transition the order to `confirmed` (that happens after the loop), so `cancelOrder` won't release the reservations — its guard is `if (order.status === 'confirmed' || order.status === 'processing')`. The reservations become orphans.

A compensating approach: wrap the successful reservation item IDs and their deltas in an array, and on any failure in the loop, iterate that array to reverse each prior reservation (using the same conditional update pattern). Alternatively, move the entire reservation to a single `plpgsql` function that runs in one transaction.

## Unrestricted invoice UPDATE RLS policy

The migration adds:

```sql
CREATE POLICY "Auth update invoices for payments" ON invoices FOR UPDATE
    USING (auth.role() = 'authenticated')
    WITH CHECK (auth.role() = 'authenticated');
```

PostgreSQL RLS policies are OR'd — if any policy grants access, the operation succeeds. This policy grants UPDATE on all columns of `invoices` to any authenticated user, bypassing the intent of the existing `invoices_manage` policy (managers only). The service layer is disciplined about which columns it writes, but RLS exists precisely to protect against clients that bypass the service layer (Supabase client SDK calls directly from the browser). A user could call `supabase.from('invoices').update({ total_amount: 0 }).eq('id', ...)` from the browser console and it would succeed.

Options: (a) replace the policy with a Postgres function that performs the payment update and restrict the policy to `USING (false)`, (b) use a `BEFORE UPDATE` trigger that rejects changes to protected columns when the user isn't a manager, or (c) at minimum, add a `WITH CHECK` clause that restricts which columns can change (though standard RLS can't do column-level checks natively — a trigger is the realistic path).

## Silent reservation leak in shipOrder and cancelOrder

Both `shipOrder` (fulfillment.ts lines 93–110) and `cancelOrder` (orders.ts lines 247–262) release reservations with the optimistic guard:

```typescript
await supabase
  .from('inventory')
  .update({ reserved_quantity: newReserved })
  .eq('product_id', item.product_id)
  .eq('warehouse_id', warehouseId)
  .eq('reserved_quantity', expectedReserved);  // guard
// No check on affected rows
```

If `expectedReserved` doesn't match (concurrent modification between the select and update), the update is a no-op. The reserved quantity is never decremented. Over time, `reserved_quantity` drifts upward, reducing the apparent available stock (`quantity - reserved_quantity`) without any record of why.

The `confirmOrder` flow correctly detects this via `.select('id')` + length check. The release paths should apply the same pattern: select the update result and either retry or throw when zero rows match.
