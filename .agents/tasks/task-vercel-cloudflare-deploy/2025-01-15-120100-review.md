# Vercel + Cloudflare Workers deployment (v2)

This is the second pass. The seven issues from v1 — webhook signature verification, auth middleware ordering, IP rate limiting, KV namespace documentation, RESEND_API_KEY documentation, field name mismatch, and notifications stub response — have all been addressed. The auth middleware now uses separate Hono sub-apps (public, webhook, protected), webhook verification uses `crypto.subtle` HMAC-SHA256 with constant-time comparison, the invoice route accepts both `order_id` and `sales_order_id`, notifications return 202 with `stub: true`, and `wrangler.toml` documents all required secrets.

Watch for: The AI chat tool-call loop can make up to 6 sequential LLM round-trips per request with no aggregate timeout, likely exceeding Workers CPU limits on non-Unbound plans (confirmed). Service-role Supabase client bypasses RLS — every query runs with admin privileges regardless of which user initiated the request (confirmed). The `/payments/create-order` and `/payments/verify` endpoints are mounted on the webhook sub-app (no JWT auth), so `created_by` is always `undefined` and any IP can create payment orders (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The worker uses three Hono sub-apps: `publicRoutes` (health), `webhookRoutes` (IP rate-limited, signature-verified), and `protectedRoutes` (JWT auth). However, the webhooks module bundles client-facing endpoints (`/payments/create-order`, `/payments/verify`) alongside the inbound webhook. Since the entire module is mounted on `webhookRoutes`, those client-facing endpoints run without JWT auth — `c.get('userId')` returns undefined, and `created_by` is stored as null.

The AI chat endpoint (835 lines) implements RAG, a 5-iteration tool-call loop, SSE streaming, and conversation persistence. Each iteration makes a sequential `fetch` to an external LLM API with no cumulative timeout or `AbortSignal`. On Workers Bundled this will hit the 30-second wall-clock limit when multiple iterations fire. The tool-call queries use the service-role Supabase client with no user-scoping, and `sanitizeFilterValue` doesn't escape Postgres `ilike` wildcards.

All Supabase queries throughout the worker bypass RLS via the service-role key. The auth boundary is entirely at the JWT layer — any authenticated user can operate on any order, customer, or product. For single-tenant (trusted staff) deployments this is intentional; for multi-tenant it's an authorization gap that needs explicit ownership checks.

<details>
<summary>Issues (5)</summary>

1. **`/payments/create-order` and `/payments/verify` have no JWT auth** — These endpoints are mounted on `webhookRoutes` (IP rate-limited only). `c.get('userId')` is undefined, so `created_by` is null and any unauthenticated caller can create payment orders. Move these two routes to `protectedRoutes` and keep only `/payments/webhook` on the webhook sub-app.
2. **AI tool-call loop has no aggregate timeout** — Up to 6 sequential LLM API calls per request with no `AbortSignal` or wall-clock guard. On Workers Bundled, this will exceed the 30-second limit when multiple iterations trigger. Add a cumulative timeout (e.g., 25 seconds) and return a partial response when it fires.
3. **Service-role client bypasses RLS for all operations** — Every route uses `createSupabaseClient(c.env)` with the service-role key. An authenticated user can call `/api/invoices/generate` with any `order_id` regardless of ownership. Either add ownership checks in each handler or use the user's JWT to create a scoped Supabase client for data reads.
4. **sanitizeFilterValue allows `%` in ilike patterns** — The function strips `,().*\\` but not `%` or `_`. A user prompting the AI with a wildcard-like query can enumerate all customers/leads via `ilike`. Escape `%` and `_` in the sanitizer.
5. **KV namespace IDs still empty in CI path** — CI will fail on first deploy. Add a pre-deploy check in the workflow that fails with a clear error message if the IDs are empty.

## Payment routes mounted without auth

The webhooks module (`workers/src/routes/webhooks.ts`) exports three POST endpoints:

- `/payments/create-order` — creates a `payment_orders` row, sets `created_by: c.get('userId')`
- `/payments/verify` — verifies Razorpay signature and marks order as paid
- `/payments/webhook` — inbound Razorpay callback, uses HMAC signature verification

In `index.ts`, the entire module is mounted on `webhookRoutes`:

```typescript
const webhookRoutes = new Hono<{ Bindings: Env }>();
webhookRoutes.use('/*', ipRateLimitMiddleware);
webhookRoutes.route('/', webhooks);
```

Only `/payments/webhook` should be here. The other two are client-initiated (the frontend calls them after user action) and need the JWT middleware to identify the user. Currently, `c.get('userId')` returns `undefined` for those routes, writing `null` to `created_by` and allowing any IP to create payment records with no authentication.

## AI tool-call loop and Workers execution limits

```typescript
while (aiResponse.tool_calls && aiResponse.tool_calls.length > 0 && iterations < maxIterations) {
  iterations++;
  // execute tools (Supabase queries)
  aiResponse = await callAIWithFallback(c.env, { ...aiOptions, messages: aiMessages });
}
```

Each `callAIWithFallback` is a `fetch` to OpenAI/Gemini/Anthropic (2-10 seconds typical). Six total calls (initial + 5 iterations) spans 15-60 seconds wall time. Workers Bundled limit is 30 seconds. No `AbortSignal`, no cumulative timer, no partial-response bailout.

The `tokensUsed` field captures only the final iteration's count, understating actual usage by up to 6x.

## ilike wildcard injection

```typescript
function sanitizeFilterValue(value: string): string {
  return value.replace(/[,().*\\]/g, '').trim();
}
```

Does not strip `%` or `_`. Used in:

```typescript
.or(`name.ilike.%${product}%,sku.ilike.%${product}%`)
```

Input `"%"` yields `name.ilike.%%%` matching every row. The `limit(5)` caps returned rows, but `get_customer_info` and `get_lead_details` use the same pattern — combined with service-role access, this enables broad enumeration through AI prompts.

## Service-role authorization scope

```typescript
export function createSupabaseClient(env: Env): SupabaseClient {
  return createClient(env.SUPABASE_URL, env.SUPABASE_SERVICE_ROLE_KEY, { ... });
}
```

Every handler uses this. The JWT middleware proves identity but no handler checks resource ownership. `/invoices/generate` with any `order_id`, `/excel/export/inventory` with no warehouse filter, tool calls querying all tables — all operate at admin scope. This is the standard pattern for trusted-staff single-tenant apps, but should be documented as a known limitation if multi-tenant is ever planned.
