# Vercel + Cloudflare Workers deployment with full backend rewrite

This change splits the application into a Vercel-hosted frontend and a Cloudflare Workers backend built on Hono. The frontend API client is renamed from `PhpApiClient` to `ApiClient` (env var `VITE_API_URL` replaces `VITE_PHP_API_URL`, with backwards-compatible fallback). The Workers backend implements the full API surface: invoice PDF generation (jsPDF), Excel import/export (SheetJS), email (Resend), notifications (stub), payment webhooks (Razorpay), and a complete AI chat endpoint with RAG, multi-provider fallback, and tool calling. CI/CD adds two deploy jobs gated to `main`.

Watch for: Payment webhook endpoint has no signature verification — any caller can mark orders paid (confirmed). The auth middleware skip logic uses string path checks that can be bypassed via route registration order (confirmed). Rate limiting fails open on KV errors and is entirely skipped for unauthenticated requests (confirmed). The `wrangler.toml` ships with empty KV namespace IDs, which will fail deployment until filled (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The frontend rename is clean — `ApiClient` falls back through `VITE_API_URL` → `VITE_PHP_API_URL` → `localhost:8080`, preserving backward compatibility during migration. All consumer imports were updated and the build passes.

The Workers backend is a substantial new subsystem (~4,500 lines) implementing every backend endpoint the PHP server previously handled, plus a full AI/RAG pipeline. The architecture is straightforward Hono routes with a shared Supabase service-role client, but the webhook routes have no cryptographic verification of inbound payloads, meaning any HTTP client can forge payment events.

The auth middleware attempts to skip certain paths using string matching in a `use('/api/*')` handler, but Hono's route registration order means the webhook route (`app.post('/api/payments/webhook', ...)`) registered before the auth middleware will already have matched before the middleware fires — the path-skip logic is dead code that gives a false sense of selective auth.

Rate limiting uses Cloudflare KV with a fail-open design: if the KV read/write throws, the request proceeds. This is a reasonable tradeoff for availability, but combined with no rate limiting for unauthenticated paths (health, webhooks), the webhook endpoint is completely unthrottled.

The CI deploy jobs are correctly gated to `main` and include a type-check step for Workers. The Vercel job uses `amondnet/vercel-action@v25` and the Cloudflare job uses `cloudflare/wrangler-action@v3`, both standard. The `wrangler.toml` ships with placeholder empty-string KV namespace IDs that will cause `wrangler deploy` to fail until real IDs are configured.

<summary>Issues (7)</summary>

1. **Webhook signature verification missing** — `POST /api/payments/webhook` accepts any JSON body and writes payment status changes to Supabase. Implement HMAC-SHA256 signature verification using `crypto.subtle` and the Razorpay webhook secret before processing events.
2. **Auth middleware ordering gives false protection** — The `app.post('/api/payments/webhook', ...)` route is registered before the `app.use('/api/*')` auth middleware. In Hono, middleware registered after a matching route handler won't run for that route. The path-check skip inside the middleware is redundant — but worse, if routes are reordered later, the assumption breaks. Pin webhook routes to a separate Hono group that explicitly skips auth.
3. **Rate limiting skipped for unauthenticated requests** — `rateLimitMiddleware` returns early (no-op) when `userId` is absent. This means all unauthenticated endpoints (health, webhooks) have no throttling. Apply IP-based rate limiting for unauthenticated paths, especially webhooks.
4. **KV namespace IDs empty in wrangler.toml** — The `id` and `preview_id` fields are empty strings. `wrangler deploy` and `wrangler dev` will fail. Either populate them or document that they must be set post-`kv:namespace create`.
5. **`RESEND_API_KEY` not declared in wrangler.toml** — The email service reads `env.RESEND_API_KEY` but the key isn't listed in `[vars]` or documented as a required secret in `wrangler.toml`. Add it to the secrets documentation or as a placeholder var.
6. **Frontend client sends `sales_order_id` but worker expects `order_id`** — `ApiClient.generateInvoice()` posts `{ sales_order_id }` while the invoice route destructures `order_id` from the body. Invoices will always return 400 ("order_id is required").
7. **Notifications endpoint is a no-op stub returning success** — `POST /notifications/whatsapp` logs to console and returns `{ success: true }` without actually delivering a message. This is fine for initial deployment but should be called out in docs or return a `202 Accepted` with a `stub: true` flag so callers know delivery didn't happen.

## Webhook authentication gap

The payment webhook handler at `workers/src/routes/webhooks.ts` has a commented-out signature verification block:

```typescript
// In production, verify signature using crypto.subtle
// const expectedSignature = hmac('sha256', secret, orderId + '|' + paymentId);
```

Without this, any party that discovers the webhook URL can post `{ "event": "payment.captured", "payload": { "payment": { "entity": { "order_id": "...", "status": "captured" } } } }` and flip order status in the database. The same file's `/payments/verify` endpoint also skips actual signature verification (same TODO comment). Both are write paths to the `payment_orders` table.

The Razorpay signature scheme uses `crypto.createHmac('sha256', secret).update(orderId + '|' + paymentId).digest('hex')`. In Workers, the equivalent uses `crypto.subtle.importKey` + `crypto.subtle.sign`. This is the single highest-priority fix.

## Auth middleware ordering and path-skip logic

In `workers/src/index.ts`, the route registration sequence is:

```
app.route('/api', health);                    // health routes mounted
app.post('/api/payments/webhook', ...);       // webhook bypass handler
app.use('/api/*', authMiddleware);            // auth middleware
app.route('/api', invoices);                  // protected routes
app.route('/api', webhooks);                  // includes /payments/webhook again
```

The `app.post('/api/payments/webhook', ...)` at line 23 is a no-op handler that just calls `next()` — it's meant to "skip" JWT auth. But since the webhooks route module (`app.route('/api', webhooks)`) is mounted *after* the auth middleware, the `/payments/webhook` POST in that module *will* go through auth. Meanwhile the standalone `app.post` at line 23 matches first and bypasses auth, but it produces no response — the request then falls through to the auth middleware's `app.use('/api/*')`. The path-check inside that middleware (`if path === '/api/payments/webhook'`) then skips auth.

This works by coincidence of Hono's evaluation order, but it's brittle. If someone reorders the route mounts or adds a catch-all, the bypass breaks silently. A cleaner pattern: mount webhook routes on a separate sub-app that doesn't apply `authMiddleware`.

## Rate limiting fail-open and coverage gaps

The rate limiter in `workers/src/middleware/rate-limit.ts` catches all KV errors and calls `next()`:

```typescript
} catch {
  // If KV fails, allow the request through
  await next();
}
```

This is a deliberate availability-over-security choice. However, the rate limiter is only applied to the AI chat route group (`aiChat.use('/*', rateLimitMiddleware)`). None of the other authenticated routes (invoice generation, Excel export, email send) are rate-limited. The AI chat limit is 30 requests/minute/user, which is reasonable for LLM calls but means other expensive operations (PDF generation, large Excel exports) are unbounded.

## Frontend ↔ Worker field name mismatch

`src/services/api.ts` sends:
```typescript
async generateInvoice(salesOrderId: string): Promise<Blob> {
  return this.request<Blob>('POST', '/api/invoices/generate', {
    sales_order_id: salesOrderId,
  });
}
```

`workers/src/routes/invoices.ts` expects:
```typescript
const body = await c.req.json<{ order_id: string; company?: Record<string, unknown> }>();
const { order_id, company } = body;
if (!order_id) {
  return c.json({ error: 'order_id is required' }, 400);
}
```

The field name discrepancy (`sales_order_id` vs `order_id`) means invoice generation will always fail with a 400 in production. Similarly, `generatePO` sends `{ purchase_order_id }` while the worker expects `{ po_id }`.

## Deployment readiness: wrangler.toml placeholders

The KV namespace configuration ships with empty IDs:

```toml
[[kv_namespaces]]
binding = "RATE_LIMIT"
id = ""
preview_id = ""
```

Wrangler validates these at deploy time and will reject the configuration. The CI deploy job will fail until someone manually fills these in after running `wrangler kv:namespace create`. This isn't a bug per se — it's standard for new projects — but the CI job lacks a guard that would surface a clear error message instead of a cryptic wrangler failure.

## AI chat: tool-call loop and token accounting

The AI chat endpoint supports up to 5 iterations of tool calling before returning. Each iteration makes a fresh LLM API call. If all 5 iterations use tool calls, that's 6 total LLM round-trips per user request — potentially 30+ seconds of wall time (and corresponding Cloudflare CPU time billing) without any intermediate timeout. Workers have a default 30-second CPU time limit on the free plan (50ms on unbundled). The `[placement] mode = "smart"` and `nodejs_compat` flags suggest Bundled plan, where the limit is 50ms CPU per invocation unless Workers Unbound is used. Five sequential `fetch` calls to OpenAI will easily exceed wall-clock limits on non-Unbound plans.

The `tokensUsed` tracking only captures the final call's token count, not the sum across iterations. If billing visibility matters, accumulate across the loop.

## Notifications as a stub

The WhatsApp/SMS endpoint builds a message string, logs it to `console.log`, and returns `{ success: true, status: 'queued' }`. Callers will believe the message was delivered. If the frontend displays "Message sent!" based on this response, users will see false confirmation. Either return a distinct status (`stub`, `dry_run`) or gate the endpoint behind a feature flag / env var that signals whether a real provider is configured.
