# CRM Pipeline: service layer, pipeline hooks, and full page rewrite

Phase 4 replaces all mock data in the CRM pages with a real Supabase-backed service layer covering lead scoring, deal pipeline management, conversion workflows, follow-up automation, and activity tracking. Two new pages (FollowUps, ConversionFunnel) and four new TanStack Query hooks wire the service layer to the UI. The migration adds `lead_scores`, `followup_rules`, and `email_sequences` tables, plus new columns on `leads` and `deals`.

Watch for: The entire service layer and all new hooks query a `crm_activities` table that does not exist in any migration — every runtime CRM operation will fail with a Postgres "relation does not exist" error (confirmed). The `performed_by` field is hardcoded to `'current-user'` across all pages despite a working `useAuth` hook being available (confirmed). `scoreAllLeads` issues N sequential queries per lead with no concurrency bound (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The blocking problem is a table name mismatch. The original schema creates an `activities` table; the new code uniformly references `crm_activities`. No migration creates this table, no rename exists, no view aliases it. Every insert, select, and update in the service layer will fail at the Postgres level. This affects scoring (activity count), follow-ups (all queries), conversion (activity logging), and the Activities page feed.

Auth identity is stubbed throughout: every `performed_by` parameter is hardcoded to the string `'current-user'`. The app has a functioning `useAuth` hook that exposes `user.id`. Activity logs, notifications, follow-up assignments, and audit trails will all record a meaningless literal rather than the actual user.

The lead scoring system uses a serial loop — `scoreAllLeads` awaits each lead individually, issuing 5 DB round-trips per lead. On a few hundred leads this will trivially exceed reasonable request timeouts.

The multi-step conversion workflows (lead → customer, deal → order) do not use transactions. If a step after the customer/order insert fails, the system is left in a partially-converted state with no rollback.

1. **Missing `crm_activities` table** — The migration never creates `crm_activities`; the existing table is `activities` with a different schema. Add a migration that either renames the table or creates `crm_activities` with the columns the service layer expects (`activity_type`, `title`, `description`, `customer_id`, `lead_id`, `deal_id`, `performed_by`, `scheduled_at`, `completed_at`).

3. **`scoreAllLeads` N+1 serial loop** — Refactor to batch-fetch activity counts (e.g., `GROUP BY lead_id`) and compute scores in-memory, or at minimum use `Promise.all` with a concurrency limit.
4. **No transactional integrity in conversion workflows** — `convertLeadToCustomer` and `convertDealToOrder` perform multiple writes sequentially; any mid-sequence failure leaves partial state. Use Supabase's `rpc` to wrap in a Postgres function, or implement compensating rollbacks.
5. **Schema column mismatch** — The TypeScript `Lead` interface uses `name`, `company`, `estimated_value`, but the `leads` DB table (001_initial_schema) has `company_name`, `contact_person`, `expected_value`. A schema migration or view is missing.
6. **RLS gap on `lead_scores`** — The policy only grants SELECT and INSERT. There is no UPDATE or DELETE policy, so score recalculation (which may need to update/replace old scores) and cleanup operations will be blocked by RLS.
7. **Misleading completion rate metric** — FollowUps page labels "completion rate" but calculates "not-yet-overdue rate." Rename or fix the formula to track actual completions.

## Missing `crm_activities` table

The `activities` table from `001_initial_schema.sql` has columns `type`, `subject`, `description`, `related_type`, `related_id`, `assigned_to`, `due_date`, `completed_at`. The service layer and hooks query `crm_activities` with a fundamentally different schema: `activity_type`, `title`, `customer_id`, `lead_id`, `deal_id`, `performed_by`, `scheduled_at`, `completed_at`. These are not just renamed columns — the entity linking model changed from polymorphic (`related_type`/`related_id`) to explicit foreign keys per entity type.

The pre-existing `useActivities.ts` hook (imported by FollowUps.tsx for `useCompleteActivity`) queries the `activities` table. So even within this PR, two different table names are used for the same concept: `activities` in the older hook and `crm_activities` in all new code. The FollowUps page imports `useCompleteActivity` from the old hook (which operates on `activities`) while `useSnoozeFollowUp` operates on `crm_activities`. A follow-up that's snoozed and then completed would hit two different tables.

Confidence: **confirmed** — grep shows no `CREATE TABLE crm_activities` in any migration file.

## Hardcoded auth identity

```tsx
// src/pages/crm/Deals.tsx:99
{ deal_id: deal.id, outcome: 'won', performed_by: 'current-user' }
```

This pattern appears in 6 locations across the new CRM pages. The `AuthContext` provides `user.id` from the Supabase session.

Confidence: **confirmed** — `useAuth` exists and is used in TopNav and AuthGuard.

## Sequential scoring and N+1

`scoreAllLeads` fetches all active lead IDs, then loops:

```ts
for (const lead of leads ?? []) {
  const score = await calculateLeadScore(lead.id);
  scores.push(score);
}
```

Each `calculateLeadScore` call makes: 1 lead fetch, 1 activity count, 1 recent-activity fetch, 1 score insert, 1 lead update = 5 DB round-trips. For 200 leads, that's 1000 sequential queries. `scoreAllLeads` is exported and available for UI consumption via the barrel; if triggered from the UI it will time out.

Confidence: **confirmed**.

## Non-transactional conversion workflows

In `conversion.ts`, `convertLeadToCustomer`:
1. Fetches lead
2. Inserts customer
3. Updates lead `converted_customer_id` and `status`
4. Inserts activity log
5. Inserts notification

If step 3 fails, a customer record exists with no back-reference from the lead. The same pattern applies to `convertDealToOrder` where a sales order can be created but the deal never updated. Supabase JS client doesn't support multi-statement transactions directly; the recommended pattern is an RPC wrapping the logic in a Postgres function, or compensating deletes on failure.

Confidence: **confirmed** — no transaction boundary exists in the code.

## Schema column name mismatch

The `leads` DDL (001_initial_schema.sql) defines:
- `company_name TEXT NOT NULL`
- `contact_person TEXT NOT NULL`
- `expected_value DECIMAL(12,2)`
- `priority INTEGER`
- `next_follow_up TIMESTAMPTZ`

The TypeScript `Lead` interface (and all service code) uses:
- `name` (not `company_name`)
- `company` (separate field, nullable)
- `estimated_value` (not `expected_value`)
- No `priority`, no `next_follow_up`

The `useLeads` hook queries `.or('name.ilike..., company.ilike...')` — these would fail at runtime if the DB columns are actually `company_name` and `contact_person`.

Confidence: **likely** — the mismatch is visible in the code, but it's possible a prior phase renamed these columns via a mechanism not captured in the migrations directory.

## FollowUps completion rate

```ts
const completionRate = totalCount > 0
  ? Math.round(((totalCount - overdueItems.length) / totalCount) * 100)
  : 100;
```

This doesn't measure completion — it measures "not yet overdue." A follow-up scheduled for tomorrow that hasn't been completed counts toward this percentage. The UI labels it "completion rate."

Confidence: **confirmed**.
