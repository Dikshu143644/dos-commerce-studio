# Production deployment infrastructure for Netlify, Railway/Render, and Supabase (v2)

This is the second review pass. All five blocking issues from v1 have been addressed: `'unsafe-inline'` removed from script-src, Railway `startCommand` removed, CI php-checks uses full `composer install`, frontend nginx listens on port 8080, and Google OAuth set to `enabled = false`. The deployment stack is now functional across all target platforms.

Watch for: Render env var names (`SMTP_USER`, `SMTP_PASS`) don't match what the PHP application reads (`SMTP_USERNAME`, `SMTP_PASSWORD`), so SMTP will silently fail on Render (confirmed). The Procfile still bypasses supervisor, identical to the removed Railway startCommand pattern (confirmed). CSP `connect-src` whitelists direct AI API domains that the browser never contacts (confirmed — dead entries, not a vulnerability).

**Verdict**: NEEDS_CHANGES

## High-level view

The Render platform config declares `SMTP_USER` and `SMTP_PASS` as env var keys, but the PHP application reads `SMTP_USERNAME` and `SMTP_PASSWORD`. Anyone deploying to Render and following the config as written will have broken email sending with no error at startup — the settings fall back to empty strings.

The Procfile (`web: php-fpm -D && nginx -g 'daemon off;'`) bypasses supervisor in the same way the now-removed Railway `startCommand` did. Heroku-compatible runtimes and any tool that reads Procfiles (Railway included, as a fallback) will skip process supervision. Since the railway.json fix was specifically to use the Dockerfile CMD, the Procfile is inconsistent with that decision.

The CSP in `public/_headers` whitelists `https://api.openai.com` and `https://generativelanguage.googleapis.com` in `connect-src`, but the frontend AI providers have runtime guards that throw before making browser-side calls to these domains. The entries are dead weight that widens the CSP surface without serving any function.

The X-Frame-Options header is set to `DENY` in `netlify.toml` but `SAMEORIGIN` in the Docker nginx configs. This means the framing policy differs between Netlify-deployed and Docker-deployed frontends — minor, but worth aligning on one value.

## Render env var naming vs. PHP expectations

The `render.yaml` declares:

```yaml
envVars:
  - key: SMTP_USER
    sync: false
  - key: SMTP_PASS
    sync: false
```

But `server/php/src/Config/settings.php` reads:

```php
'username' => $_ENV['SMTP_USERNAME'] ?? '',
'password' => $_ENV['SMTP_PASSWORD'] ?? '',
```

And `docker-compose.yml` passes:

```yaml
- SMTP_USERNAME=${SMTP_USERNAME}
- SMTP_PASSWORD=${SMTP_PASSWORD}
```

The Render config is the outlier. Someone deploying on Render and setting `SMTP_USER` as instructed will have the PHP app silently fall back to empty credentials, and emails will fail at send time (likely with an SMTP auth error), not at startup. The fix is renaming the render.yaml keys to `SMTP_USERNAME` and `SMTP_PASSWORD`.

## Procfile still bypasses supervisor

The v1 review flagged `railway.json`'s `startCommand` for bypassing supervisor. That was fixed by removing the startCommand entirely. However, the Procfile contains the same pattern:

```
web: php-fpm -D && nginx -g 'daemon off;'
```

Railway falls back to Procfiles when no `startCommand` is specified in `railway.json` *and* the Dockerfile has no CMD — but since the Dockerfile does have a CMD, Railway will use the CMD and the Procfile has no effect *on Railway*. However, if the app is ever deployed to Heroku, Dokku, or any Procfile-honoring platform, it will bypass supervisor. The Procfile should either match the Dockerfile CMD (launching supervisord) or be removed, since the project is Docker-first on both Railway and Render.

## OPcache validate_timestamps=0 in dev volumes

This concern was raised in v1 and remains unaddressed. The PHP Dockerfile bakes in `opcache.validate_timestamps=0`, and `docker-compose.dev.yml` mounts source volumes into that same image. Developers using the dev override will see stale bytecode until they restart the container. The dev compose should set `PHP_OPCACHE_VALIDATE_TIMESTAMPS=1` or mount a php.ini override that re-enables timestamp validation. This is a developer-experience issue, not a production bug.
