# Production deployment infrastructure for Netlify, Railway/Render, and Supabase

This change adds the complete deployment stack for StockFlow: Netlify configuration for the React SPA, production-hardened Docker images for both the frontend (nginx) and the PHP backend (PHP-FPM + nginx + supervisor), Railway/Render platform configs, a 4-job CI/CD pipeline in GitHub Actions, Supabase local config and Edge Function deployment docs, frontend config validation and monitoring scaffolding, and Vite chunk splitting. The approach is platform-redundant — both Railway and Render configs ship — with Docker as the common deployment primitive for the PHP tier.

Watch for: CSP allows `'unsafe-inline'` for scripts, which significantly weakens XSS protection (confirmed). The `railway.json` startCommand conflicts with the Dockerfile's supervisor-based entrypoint (confirmed). The CI pipeline's `php-checks` job runs `vendor/bin/phpunit` after `composer install --no-dev`, which strips PHPUnit from the vendor directory (confirmed). The frontend Dockerfile runs nginx as a non-root user but the nginx.conf binds to port 80, which typically requires root on some container runtimes (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The Netlify layer is straightforward — build settings, SPA redirect, and security headers across `netlify.toml`, `public/_headers`, and a serverless health function. The headers file adds a CSP that whitelists Supabase, OpenAI, and Google AI endpoints for `connect-src` but permits `'unsafe-inline'` on `script-src`, negating much of the XSS protection CSP exists to provide.

The PHP container is the most complex piece: a multi-stage Dockerfile using `php:8.4-cli-alpine` for dependency resolution (to avoid the PHP 8.5 incompatibility in the stock composer image) and `php:8.4-fpm-alpine` for production, with supervisor orchestrating PHP-FPM and nginx. The Railway config declares its own `startCommand` that bypasses supervisor, creating a conflict where Railway would try to launch php-fpm and nginx directly rather than using the container's CMD.

The CI pipeline splits into lint-and-typecheck → build → php-checks → docker-build. The `php-checks` job installs with `--no-dev` then attempts to run PHPUnit, which won't exist in the vendor tree. This job will fail on every run unless the install step removes the `--no-dev` flag.

The frontend config module (`src/lib/config.ts`) adds runtime validation that throws on missing env vars in production builds but silently uses fallback values in development. Vite chunk splitting isolates vendor, UI, charts, and query libraries into separate bundles. The monitoring module is scaffolding — exported utilities with no call sites yet in this diff.

<summary>Issues (5)</summary>

1. **CSP unsafe-inline for scripts** — `public/_headers` sets `script-src 'self' 'unsafe-inline'`, which lets injected inline scripts execute. Remove `'unsafe-inline'` and use nonces or hashes if inline scripts are needed.
2. **Railway startCommand bypasses supervisor** — `railway.json` specifies `php-fpm -D && nginx -g 'daemon off;'` but the Dockerfile CMD is `supervisord`. Railway will use its startCommand, skipping process supervision and log routing. Either remove the startCommand or align it with `supervisord -c ...`.
3. **PHPUnit after --no-dev install** — CI job `php-checks` runs `composer install --no-dev` then `vendor/bin/phpunit`. PHPUnit is a dev dependency and won't be present. Use `--no-dev` only for the syntax check, or run a separate install without `--no-dev` before PHPUnit.
4. **Non-root nginx on port 80** — The frontend Dockerfile switches to `appuser` before running nginx on port 80. Some container runtimes (notably Render's free tier, some Kubernetes setups) may reject binding to privileged ports as non-root. Consider listening on 8080 with a port mapping.
5. **Google OAuth enabled with empty credentials** — `supabase/config.toml` sets `[auth.external.google] enabled = true` with empty `client_id` and `secret`. If deployed to a Supabase project without overriding, Google OAuth will be enabled but broken, potentially confusing users seeing a login button that fails.

## CSP policy and connect-src whitelist

The CSP in `public/_headers`:

```
script-src 'self' 'unsafe-inline'
```

This permits any inline `<script>` tag to execute. The application uses Vite-bundled modules, so `'unsafe-inline'` is likely only needed for Vite's dev server injection. In production builds, Vite doesn't inject inline scripts unless explicitly configured to. Removing `'unsafe-inline'` and testing the production build would confirm whether any legitimate inline scripts break.

The `connect-src` directive whitelists `https://api.openai.com` and `https://generativelanguage.googleapis.com` directly. The existing AI architecture routes through a Supabase Edge Function (`ai-chat`), so these direct API domains shouldn't be needed from the browser. Their presence suggests either the frontend makes direct AI API calls (which would leak API keys client-side) or they're a precautionary whitelist that should be removed to tighten the CSP. Worth verifying which pattern is in use.

## Railway startCommand vs. Dockerfile CMD

The PHP Dockerfile uses supervisor to manage both PHP-FPM and nginx:

```dockerfile
CMD ["/usr/bin/supervisord", "-c", "/etc/supervisor/conf.d/supervisord.conf"]
```

But `railway.json` declares:

```json
"startCommand": "php-fpm -D && nginx -g 'daemon off;'"
```

Railway's `startCommand` overrides the Docker CMD. When deployed on Railway, supervisor won't run — no automatic process restart if PHP-FPM crashes, no unified log routing, and a different process tree than what's tested locally with `docker compose`. The `Procfile` has the same pattern. On Render, `render.yaml` doesn't specify a start command, so it falls back to supervisor correctly. The inconsistency is Railway/Procfile-specific.

## CI pipeline: PHPUnit without dev dependencies

```yaml
- run: composer install --no-dev --optimize-autoloader
- run: find src -name "*.php" -exec php -l {} \;
- run: vendor/bin/phpunit
```

After `--no-dev`, the `vendor/bin/phpunit` binary won't exist. The syntax check will pass, but the test step will fail with "No such file or directory" on every PR. The fix is either splitting into two composer installs or dropping `--no-dev` in CI where the goal is to run the full test suite.

## OPcache validate_timestamps=0 with dev volume mounts

The PHP Dockerfile sets `opcache.validate_timestamps=0` — correct for an immutable production image. However, `docker-compose.dev.yml` mounts source files into the container via volumes (`./server/php/src:/var/www/html/src`). If a developer uses the dev override with this same production image, OPcache will serve stale bytecode and file changes won't take effect until the container restarts. The dev compose should set an environment variable or PHP ini override to re-enable timestamp validation.

## PHP container runs supervisor as root

The PHP Dockerfile's supervisor config sets `user=root`. PHP-FPM workers run as `www-data` and nginx drops privileges after binding, but PID 1 remains root. Railway and Render tolerate this. If the container moves to a runtime enforcing non-root policies (Cloud Run, some Kubernetes clusters), it will need restructuring — the port 80 bind is the constraint that drives this pattern.

## Cron health check: liveness without correctness

The cron container's health check:

```yaml
healthcheck:
  test: ['CMD', 'pgrep', '-f', 'scheduler']
```

This matches the parent `sh -c` process containing "scheduler" in its command string, so it reports healthy as long as the shell loop is alive. A cron that exits with errors on every execution will still report healthy. This is a liveness check, not a correctness check — the distinction matters if health is used for alerting.
