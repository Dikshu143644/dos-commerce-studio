# Auth system redesign: role-based access, OTP registration, split login pages (v1)

This change overhauls the authentication flow of the StockFlow SPA. The Login page is stripped of its Google OAuth button and rebuilt as a professional centered-card design. A parallel Staff Portal login page lives at `/staff-login`. Registration drops the role selector (hardcoding `viewer`) and gains a 3-step flow: credentials, phone with country-code picker, OTP verification. The AuthContext now fetches the user's profile and role from the database after login and exposes `userRole` and `profile` to the tree. The AuthGuard uses that role to enforce route restrictions, and the Sidebar filters its nav sections by the same role mapping.

**Verdict**: NEEDS_CHANGES

## Issues

1. **Dead `loginWithOAuth` export** - Remove `loginWithOAuth` from AuthContext and the `AuthState` interface. It still references `supabase.auth.signInWithOAuth` for Google/GitHub, creating a latent surface if any code path ever calls it. No UI uses it.

2. **OTP `signInWithOtp` may clobber email session** - Replace `signInWithOtp` with `supabase.auth.updateUser({ phone })` or a custom OTP delivery mechanism to attach a phone to the existing session instead of initiating a separate phone-auth flow.

3. **Client-only role enforcement** - Out of scope for this frontend-only change. Note as a known limitation. (DO NOT FIX - requires backend changes)

4. **Duplicated login form logic** - Extract the submit handler, rate-limit countdown, and debounce pattern into a shared hook (e.g., `useLoginForm`) used by both Login and StaffLogin. Currently ~120 lines are copy-pasted.

5. **Profile + role double-query on every auth event** - Combine into a single join query (`profiles.*, roles(name)`) or cache the result until the user ID changes, to avoid unnecessary round-trips on session refresh events.

6. **Profile creation race with database trigger** - The frontend upsert with `onConflict: 'id'` handles this gracefully already. The code acknowledges this. (ACCEPTABLE as-is)

7. **Manager access to `/settings/users`** - Per the user requirements: "Manager sees everything + approvals" and "Admin sees everything + settings + user management". Managers should NOT have access to Settings. Fix the sectionsByRole and AuthGuard.
