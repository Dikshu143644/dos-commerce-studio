# Auth system redesign: role-based access, OTP registration, split login pages

This change overhauls the authentication flow of the StockFlow SPA. The Login page is stripped of its Google OAuth button and rebuilt as a professional centered-card design. A parallel Staff Portal login page lives at `/staff-login`. Registration drops the role selector (hardcoding `viewer`) and gains a 3-step flow: credentials → phone with country-code picker → OTP verification. The AuthContext now fetches the user's profile and role from the database after login and exposes `userRole` and `profile` to the tree. The AuthGuard uses that role to enforce route restrictions, and the Sidebar filters its nav sections by the same role mapping.

Watch for: the `loginWithOAuth` method is still exported and wired into the provider despite all OAuth UI being removed (confirmed dead code). The OTP step uses `signInWithOtp` against the same session that was just created by `signUp`, which will overwrite the email-based session if the phone provider is configured — whether intentional or accidental determines if users lose email verification (likely). The AuthGuard enforces restrictions purely in the client; no corresponding RLS or middleware is mentioned, so a direct API call from devtools bypasses all gating (confirmed client-only enforcement).

**Verdict**: NEEDS_CHANGES

## High-level view

The login pages (customer and staff) share identical credential logic and rate-limit handling but are separate files with fully duplicated submit handlers, countdown effects, and toast parsing. The design distinction is branding only — a shield icon vs an "S" logo — so this duplicates ~120 lines of form logic that will drift.

The AuthContext issues two sequential queries (profile fetch, then role fetch by ID) on every auth state change including tab-focus events. Without caching or a single joined query, this creates unnecessary round-trips on session refresh.

Registration's OTP step calls `supabase.auth.signInWithOtp({ phone })` after the user has just signed up with email+password. If the phone provider is ever configured, this creates a competing auth session for the phone number, potentially logging the user in as a different identity or resetting the email session Supabase issued moments earlier.

Client-side route gating via prefix matching in AuthGuard protects the React tree but not the data layer. The underlying Supabase queries in each page component will still execute during the brief render before the redirect fires, succeeding or failing depending solely on RLS policies outside this diff.

7. **Manager access to `/settings/users`** — Managers get Settings nav and are not blocked by AuthGuard, giving them access to user and role management. If only admins should manage users, add `manager` to the blocked roles for `/settings`.

## OTP session conflict with `signInWithOtp`

In `OTPVerification.tsx`, the component fires `supabase.auth.signInWithOtp({ phone })` on mount. The "signIn" family of methods in Supabase is designed to create or resume a session around that credential. The graceful fallback (`providerUnavailable`) currently masks this because the call fails before issuing a token. The moment an SMS provider goes live, the OTP verification step will either:

- create a second auth identity (phone) that competes with the email identity just created, or
- overwrite the current session token with a phone-session token, losing the email confirmation flow.

The safer pattern is `supabase.auth.updateUser({ phone })` followed by a manual OTP send via the Cloudflare Worker already in the codebase, then verifying the OTP server-side and marking the phone as confirmed in the `profiles` table.

## Dead OAuth surface in AuthContext

```typescript
const loginWithOAuth = useCallback(async (provider: 'google' | 'github') => {
  const { error } = await supabase.auth.signInWithOAuth({
    provider,
    options: { redirectTo: `${window.location.origin}/` },
  });
  if (error) throw error;
}, []);
```

No component calls this after the OAuth button removal. If a future developer finds `loginWithOAuth` in the hook's return type, they may wire it into new UI without realizing the providers aren't configured, creating a dead-end login path or — worse — re-enabling OAuth silently if the Supabase project later adds Google. Remove entirely.

## Client-side route gating without server enforcement

The AuthGuard uses path-prefix matching to redirect viewers away from `/inventory`, `/crm`, `/procurement`, `/reports`, and `/settings`. Each page component behind those routes makes its own Supabase queries. If a viewer types `/inventory/products` into the URL bar, React Router renders the component briefly before the redirect Navigate fires. During that brief render, the component's `useEffect` fires the Supabase query. Whether that query returns data depends entirely on whether the `products` table has RLS restricting by role — which is not part of this diff. If RLS is permissive (common during development), the viewer's client receives the full dataset even though they're redirected away from the page.

The fix is either adding RLS checks or gating each page's data-fetching hook on `userRole` before issuing the query.

## Profile creation race condition

In `AuthProvider.signup`, after `supabase.auth.signUp` succeeds, the code immediately calls `createProfileForUser`. That function queries the `roles` table for the viewer role ID, then upserts into `profiles`. If the Supabase project also has a database trigger that creates a profile on `auth.users` INSERT (the comment in the code acknowledges this possibility), the frontend upsert and the trigger race. The `onConflict: 'id'` clause prevents a crash, but whichever write lands second wins the `full_name`, `phone`, and `role_id` values. If the trigger sets a different default (or null for phone/name since it only has email), the user's name and phone get overwritten to empty.

The safest fix: either rely solely on the frontend upsert (remove the trigger) or rely solely on the trigger (pass all metadata via `options.data` and let the trigger read `raw_user_meta_data`). Doing both creates a last-writer-wins race.

## Manager role and Settings access

The Sidebar `sectionsByRole` grants `manager` access to the "Settings" section (which includes `/settings/users`, `/settings/roles`). The AuthGuard only blocks `viewer`, `client`, and `staff` from `/settings` — managers fall through to the permissive default. A manager with access to `/settings/users` can view and potentially modify user roles. If the intent from the user instruction ("Admin → sees everything + settings + user management") is that only admins manage users, the guard should block managers from `/settings` as well, or at minimum from `/settings/users` and `/settings/roles`.
