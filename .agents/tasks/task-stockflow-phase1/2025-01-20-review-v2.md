# Fix pass for AI proxy, auth wiring, enum alignment, and sequence generators

The fix commit addresses 6 of 8 issues from the v1 review. TypeScript enums now match their SQL counterparts exactly. Auth forms call the real Supabase methods (login, signup, resetPassword, Google OAuth). The AI provider layer introduces a `ProxyProvider` gated by `VITE_AI_PROXY_URL` and blocks direct provider usage in the browser with runtime guards. SQL number generators use PostgreSQL `SEQUENCE` objects via `nextval()`. The remaining two items — no data layer and no test files — are acknowledged Phase 1 scope boundaries. Watch for: `.env.example` still advertises direct API key vars without documenting the proxy URL (confirmed); Login page bypasses AuthContext to call `supabase.auth.signInWithOAuth` directly (confirmed, minor architectural inconsistency).

**Verdict**: APPROVED

## High-level view

The enum fix is complete — all 7 type unions in `database.ts` now mirror the SQL `CREATE TYPE` definitions, and mock data across pages uses the corrected values.

Auth forms are wired through `useAuth()` for login, signup, and password reset. The Google OAuth path calls `supabase.auth.signInWithOAuth` directly rather than routing through AuthContext — a minor encapsulation leak, functionally correct since `onAuthStateChange` picks up the session, but it creates a direct Supabase dependency in the component layer that the other auth pages avoid.

The AI provider restructure blocks all direct browser-side API calls via `isConfigured()` guards and runtime throws. `.env.example` still documents `VITE_OPENAI_API_KEY`, `VITE_GEMINI_API_KEY`, and `VITE_ANTHROPIC_API_KEY` without mentioning `VITE_AI_PROXY_URL`, which could mislead a developer into setting keys that will never be used.

The sequence fix replaces `COUNT(*)+1` with `nextval()` on three dedicated sequences, eliminating both the concurrency race and post-deletion collisions.

## `.env.example` documents unused direct-key vars

The `.env.example` file lists:

```
VITE_AI_PROVIDER=openai
VITE_OPENAI_API_KEY=sk-your-openai-key
VITE_GEMINI_API_KEY=your-gemini-key
VITE_ANTHROPIC_API_KEY=sk-ant-your-anthropic-key
```

None of these are consumed by the browser runtime — the `isConfigured()` guards return `false` when `window` exists, and `VITE_AI_PROVIDER` has no reference anywhere in the source. A developer following `.env.example` would set keys that have no effect. `VITE_AI_PROXY_URL` (the one variable that activates AI in the browser) is documented only in a code comment in `providers.ts`.

## OAuth uses raw Supabase client in Login.tsx

`Login.tsx` imports `supabase` directly:

```typescript
import { supabase } from '@/lib/supabase';
// ...
const { error: oauthError } = await supabase.auth.signInWithOAuth({
  provider: 'google',
  options: { redirectTo: `${window.location.origin}/` },
});
```

Every other auth operation routes through `AuthContext`. This one bypasses it, creating a hard dependency on the Supabase client that the other auth pages don't have. If the auth provider is swapped (Clerk, Auth0), this call won't be caught by refactoring `AuthContext` alone.
