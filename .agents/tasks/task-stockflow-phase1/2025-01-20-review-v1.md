# Greenfield React SPA for inventory and CRM management

StockFlow Phase 1 delivers a complete frontend scaffold: 24 route-level pages, 19 UI primitives, a layout system with collapsible sidebar and glassmorphism theme, Supabase auth integration, an AI chat layer with multi-provider fallback, and a SheetJS-based Excel service. The database schema (3 migration files) defines 20 tables with RLS policies and stock-quantity triggers. The entire frontend currently runs on hardcoded mock data — no Supabase queries are wired up — so this is a design-time shell, not a connected application. Watch for: API keys exposed client-side in the AI provider layer (confirmed); sequential number generators that race under concurrent inserts (confirmed); enum drift between TypeScript types and the SQL schema (confirmed); and zero test coverage.

**Verdict**: NEEDS_CHANGES

## High-level view

The architecture follows a standard Vite SPA pattern well: lazy-loaded routes, context-based auth, TanStack Query configured but unused, and a clean path-aliased folder structure. Code organization is easy to navigate — `services/`, `pages/`, `components/ui`, `components/shared`, `components/layout` — and the design system tokens flow from a single CSS theme block through consistent component usage.

The AI service layer is designed to run entirely in the browser, calling OpenAI/Gemini/Anthropic APIs directly from client-side code using API keys stored in VITE_ environment variables. This architecture leaks secret keys to any user who opens DevTools. The Anthropic provider will additionally fail at runtime because the Anthropic API rejects browser requests (no CORS).

The database schema is well-structured with proper foreign keys, indexes, and RLS, but the sequential number generators (`generate_po_number`, `generate_order_number`, `generate_invoice_number`) use `SELECT COUNT(*) + 1` which produces duplicates under concurrent load. The enum values defined in SQL diverge from the TypeScript type unions in `src/types/database.ts` — the schema will reject inserts with the frontend's enum values.

Every page renders hardcoded mock arrays. The `QueryClient` is mounted at the root but never used for data fetching. There is no data-access layer, no Supabase query hooks, and no error boundary wrapping the route tree. The app is a working UI prototype, not a connected system.

1. **AI API keys in client bundle** — VITE_OPENAI_API_KEY, VITE_GEMINI_API_KEY, VITE_ANTHROPIC_API_KEY are read at runtime in the browser and sent directly to third-party APIs. Move AI calls behind a backend proxy or edge function.
2. **Anthropic CORS failure** — The Anthropic API does not serve CORS headers; the `AnthropicProvider` will always fail in browsers. Route through a server-side proxy.
3. **Gemini API key in URL** — `GeminiProvider` passes the API key as a query parameter, exposing it in access logs, browser history, and referrer headers. Use a header-based auth mechanism or server proxy.
4. **Sequential number generators race** — `generate_po_number()`, `generate_order_number()`, and `generate_invoice_number()` all use `COUNT(*) + 1`, which yields duplicate numbers under concurrent inserts. Use a `SEQUENCE` or `nextval()`.
5. **TypeScript/SQL enum mismatch** — `database.ts` defines values (`'pending'`, `'submitted'`, `'individual'`, `'business'`, `'discovery'`, etc.) that don't exist in the SQL enums (`'sent'`, `'regular'`, `'wholesale'`, `'qualification'`, etc.). Inserts will be rejected by PostgreSQL.
6. **No data layer** — TanStack Query is installed and configured but zero queries or mutations exist. All 24 pages render hardcoded mock data with no fetch logic.
7. **Login form doesn't call AuthContext** — The `Login` page's `onSubmit` does a `console.log` and `setTimeout` instead of calling `login()` from `useAuth()`. Users cannot actually log in.
8. **Zero test coverage** — No test files, no test runner installed (no Vitest/Jest in devDependencies), no CI test step.

## AI provider layer calls third-party APIs from the browser

The `providers.ts` file instantiates three AI providers — OpenAI, Gemini, Anthropic — and calls their HTTP APIs directly from client-side JavaScript using `fetch`. The API keys are sourced from `import.meta.env.VITE_*` variables, which Vite statically inlines into the production bundle. Any user can extract these keys from the compiled JavaScript.

```typescript
// providers.ts
const apiKey = import.meta.env.VITE_OPENAI_API_KEY;
const response = await fetch('https://api.openai.com/v1/chat/completions', {
  headers: { Authorization: `Bearer ${apiKey}` },
  ...
});
```

The Anthropic API does not support CORS, so the `AnthropicProvider.chat()` method will always throw a network error in any browser environment. The Gemini provider appends the API key as a `?key=` query parameter, which leaks through server access logs, browser history, and the Referer header on subsequent navigations.

The `chatWithFallback` function catches errors silently (`console.warn`) and falls through to a mock response generator. This means in production without a proxy, users always get canned responses — a silent functional failure.

## Sequential number generators will produce duplicates

The three number-generation functions in `003_functions.sql` all follow the same pattern:

```sql
SELECT COUNT(*) + 1 INTO v_count FROM purchase_orders;
v_number := 'PO-' || LPAD(v_count::TEXT, 6, '0');
```

`COUNT(*)` is not transactionally isolated between concurrent sessions. Two simultaneous inserts will read the same count and produce the same number, violating the UNIQUE constraint on `po_number`. After any deletion, subsequent numbers will also collide with existing records. The fix is a PostgreSQL `SEQUENCE`:

```sql
CREATE SEQUENCE po_number_seq;
-- then: 'PO-' || LPAD(nextval('po_number_seq')::TEXT, 6, '0')
```

## TypeScript enum values diverge from SQL schema

The SQL `CREATE TYPE` definitions and the TypeScript union types in `database.ts` disagree on multiple enums:

- **customer_type**: SQL defines `'regular' | 'wholesale' | 'retail' | 'distributor'`; TypeScript defines `'individual' | 'business'`.
- **deal_stage**: SQL defines `'qualification' | 'needs_analysis' | 'proposal' | 'negotiation' | 'closed_won' | 'closed_lost'`; TypeScript defines `'discovery' | 'proposal' | 'negotiation' | 'contract' | 'closed_won' | 'closed_lost'`.
- **order_status**: SQL omits `'pending'` but includes `'confirmed'`; TypeScript has `'pending'` and `'confirmed'`.
- **po_status**: SQL uses `'sent' | 'confirmed' | 'partially_received' | 'received' | 'cancelled'`; TypeScript uses `'submitted' | 'approved' | 'received' | 'partially_received' | 'cancelled'`.
- **lead_source**: SQL includes `'advertisement'`; TypeScript includes `'email'` (absent from SQL).
- **notification_type**: SQL defines `'info' | 'warning' | 'success' | 'error' | 'reminder'`; TypeScript defines `'info' | 'warning' | 'error' | 'success' | 'stock_alert' | 'order_update' | 'crm_activity'`.
- **agent_type**: SQL defines `'inventory' | 'sales' | 'procurement' | 'finance' | 'excel' | 'general'`; `database.ts` defines `'demand_forecast' | 'inventory_optimizer' | 'crm_analyzer' | 'general'`.

When the data layer is connected, inserts and reads will break on these mismatches. One authoritative source (either generated from SQL or a shared definition) should drive both.

## Login form is disconnected from auth

The `Login.tsx` page imports `useForm` with Zod validation but its `onSubmit` handler does:

```typescript
const onSubmit = async (data: LoginFormData) => {
  setIsLoading(true);
  console.log('Login attempt:', data.email);
  await new Promise((resolve) => setTimeout(resolve, 1500));
  setIsLoading(false);
};
```

It never calls the `login()` function from `AuthContext`. The `AuthGuard` checks `user` from the Supabase session, so users can never pass the guard without the Supabase `signInWithPassword` call. The Google OAuth button also has no handler beyond UI rendering.

## No data-access layer or React Query usage

`@tanstack/react-query` is configured at the root with a `QueryClient` (5-minute stale time, 1 retry), but zero `useQuery` or `useMutation` hooks exist anywhere in the codebase. Every page constructs its own `const mockProducts = [...]` or `const mockLeads = [...]` array at module scope. There are no Supabase query functions, no API service layer, and no `queryClient.invalidateQueries` calls. The "Add Product" form logs to the console; the "Add Lead" dialog closes without persisting.

This is acknowledged as a Phase 1 shell, but the absence of even one connected query means the data-flow architecture is untested. A `src/services/api/` or `src/hooks/queries/` layer with typed Supabase queries would validate that the auth, RLS, and type system work end-to-end.

## RLS policy overlap and unrestricted SELECT

Every table grants `SELECT` to all authenticated users (`USING (true)`). For an enterprise inventory system, this means any authenticated user — regardless of role or branch — can read all customers, all deals, all financial data, and all suppliers. Whether this is intentional depends on the access model, but it's worth calling out: the RLS policies enforce write restrictions by role but are completely open on reads.

Some tables have overlapping policies that may conflict. For example, `leads` has both a `leads_manage` policy (`FOR ALL`) and a `leads_insert` policy (`FOR INSERT`). PostgreSQL applies permissive policies with OR semantics, so this works, but the `leads_insert` policy is redundant — any role allowed by `leads_insert` is already covered by `leads_manage`'s `USING` clause for the `INSERT` operation. The same pattern appears on `deals`.

## Zero test coverage

No test runner is installed (`vitest`, `jest`, or `@testing-library/react` are absent from `devDependencies`). No test files exist in the project. The GitHub Actions workflow (if present) doesn't run tests. For a production system handling financial data and access control, the complete absence of tests — even for the AI router logic, the Excel parser, or the auth guard — is a gap that grows more expensive to close over time.

The AI intent router (`router.ts`) and Excel column-mapping logic (`parser.ts`) are pure functions with no side effects — ideal candidates for unit tests that would take minutes to write.
